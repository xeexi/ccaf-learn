セクション

ツール定義は3つの部品でできている

name（呼び名）、description（いつ使うか）、input_schema（何を渡すか）。判断に効くのは description です。

図の読み方

  1. 1中央の枠が1つの道具ぶんの定義。3段に分かれています。
  2. 2name ─ 呼び名。短く一意に。
  3. 3description ─ 右の注記のとおり、Claude が「使うかどうか」を判断する材料はここだけです。コードの中身も実際の挙動も見ていません。
  4. 4input_schema ─ 渡す引数の型・必須・選べる値。誤用を防ぐ枠です。

だから道具が呼ばれないときに直すのは、まず descriptionです。しかも「何をするか」ではなく「いつ使うか」を書きます。

書き直しの型 ✗ 何をするかだけ："返金規定を取得する"
○ 何をするか＋いつ呼ぶか＋いつ呼ばないか：
"返金規定を取得する。返金の可否・期限・金額に触れる前に必ず呼ぶ。一般的な配送の質問には使わない"
誤解「description はコードのコメントのようなもの。人間が読む用」 実際はプロンプトの一部です。しかも常にコンテキストを消費しています（前提編）。丁寧に、しかし冗長にならないよう書きます。

ポイントdescription に書くべきは「何をするか」より「どんなときに使うか」。判断の条件を言語化する。

ツールの粒度

数が多いと選べなくなり、1つに詰め込みすぎると引数が複雑になって間違えます。

図の読み方

  1. 1左が細かすぎる例。似た道具が8個並んでいて、どれを選べばよいか判断できません。
  2. 2中央が大きすぎる例。道具は1個ですが、引数が6つあります。
  3. 3引数が増えると、正しい組み合わせは限られるのに、選べる組み合わせは膨大になります。「delete なのに dryrun を付け忘れた」のような事故が起きます。
  4. 4右がちょうどよい例。業務の1動作＝1ツールです。
大きすぎる道具が壊れる理由 do_everything(action, mode, target, format, dryrun, …)
引数が6つあれば、正しい組み合わせは限られるのに、選べる組み合わせは膨大です。「action=delete なのに dryrun を付け忘れた」のような事故が起きます。

目安は「人間の担当者が1回でやる仕事の単位」。注文を探す、注文の詳細を見る、返金を実行する ─ これくらいの粒度です。

ポイント目安は「人間の担当者が1回でやる仕事の単位」。細かすぎれば選べず、大きすぎれば引数を間違える。

セクション

失敗は読める形で返す

ツールの失敗は「読める文章」で返す

例外で止めるとループが死にます。何が起きたかを言葉で返せば、Claudeは自分で直して再試行できます。

図の読み方

  1. 1左（赤）が落とす・黙る場合。例外を投げる、「エラー」とだけ返す、空文字を返す。
  2. 2その下がどうなるか。どちらに転んでも、モデルは同じ引数でもう一度呼びます。何が悪かったかを渡していないので、直しようがないからです。
  3. 3右（緑）が読める形で返す場合。何が起きたかを、そのまま文章で tool_result に入れます。
  4. 4その下では、引数を直して呼び直せています。つまり返す文の質が、そのまま再試行の質になります。「エラーが発生しました」では、何も直せません。
返す文に入れる2つ ① 何が起きたか：「order_id 'A12' に一致する注文がありません」
② どう直せるか：「ID は 'A-12' のようにハイフンを含む形式です」
①だけだと、同じ間違いを繰り返すことがあります。
誤解「親切にエラーを返せば、あとは勝手に直してくれる」 実際は直せないまま無限に再試行することがあります。再試行の上限は外側で持つ（Domain 1の反復上限）ことをセットで用意します。

ポイント返す文には「何が起きたか」と「どう直せるか」を両方入れる。ただし無限に再試行させないよう、回数の上限は外側で持つ。

実物を見る ─ 失敗を返す tool_result

上の考え方を、実際にアプリが送る JSON で確認します。

ツールが失敗したときに、アプリが送るもの

{ "role": "user", "content": [1
  { "type": "tool_result",
    "tool_use_id": "toolu_01A...",2
    "content": "order_id 'A12' に一致する注文がありません。IDは 'A-12' の形式です",3
    "is_error": true4 } ] }
  1. 1失敗でも成功でも、送る形は同じです。role: "user" のメッセージとして返します。例外を投げてループを止めるのではなく、こう返す、という話でした。
  2. 2どの要求に対する結果かの対応づけ。tool_use の id をそのまま入れます。ずれると会話が壊れます。
  3. 3ここが本体。Claudeが読むのはこの文章です。「何が起きたか」＋「どう直せるか」を書きます。
  4. 4is_error: true は「これは失敗だ」という印。付けてもループは止まりません。止めるためのフラグではない、というのが試験で狙われるところです。

ポイントis_error は処理を止めるためのものではない。Claudeは content の文章を読んで次を決めるので、直し方をそこに書く。止めるのは外側の反復上限。

※ 同じ user メッセージに文章も添えたい場合は、tool_result を先に置きます。文章を先に書くと 400 エラーになります。content は文字列でも、ブロックの配列でもかまいません。

セクション

MCP という差込口

MCP＝ツールをつなぐ共通の差込口

アプリごとに個別実装していた接続を、共通の規格にまとめたものです。作る量が「掛け算」から「足し算」になります。

図の読み方

  1. 1「MCPなし：N × M 本」（左）── アプリ3つ×サービス3つで線が9本。すべて個別に実装したものです。
  2. 2「MCPあり：N ＋ M 本」（右）── 中央の規格を経由するので3＋3 の6本。効き目が出るのは増やすときです。アプリを1つ足すと、左では3本増え、右では1本しか増えません。
  3. 3下の帯が3層の呼び名。設問はこの語彙で書かれるので、どれがどれかだけ押さえます ── 動かす側がホスト、つながれる側がサーバです。

ポイント「新しいサービスを繋ぎたい」という要件では、独自実装より既存の MCP サーバを使うのが素直な答えになる。

3層の関係と、よくある誤解

たとえるなら

USBです。規格が決まる前は機器ごとに専用ケーブルが必要でしたが、差込口の形を決めたことで、作る量が掛け算から足し算になりました。賢さが変わるのではなく、つなぐ手間が変わります。

3層の関係 ホスト（Claude Code など、実際に動かすアプリ）
─ クライアント（つなぐ側の口）
─ サーバ（Slack、GitHub、DB など、つながれる側）
サーバが提供できるのは tools だけではありません。resources（読める資料）や prompts（定型の手順）も渡せます。
誤解「MCP を使うとモデルが賢くなる／速くなる」 実際は賢さは変わりません。変わるのはつなぐ手間だけです。「新しいサービスと連携したい」という要件で、自前実装より既存の MCP サーバを選ぶのはそのためです。

ポイント「新しいサービスを繋ぎたい」という要件では、独自実装より既存の MCP サーバを使うのが素直な答えになる。

実物を見る ─ .mcp.json でサーバを登録する

MCPサーバをどこに書くかで、誰に見えるかが変わります。チームで共有したいならプロジェクト直下の .mcp.json です。

プロジェクト直下の .mcp.json

{
  "mcpServers": {1
    "shared-server": {
      "type": "http",2
      "url": "https://example.com/mcp" },
    "db-tools": {
      "command": "npx",3
      "args": ["-y", "@example/db-server"],
      "env": { "DB_URL": "${DB_URL}" } }4
  }
}
  1. 1mcpServers の下に、サーバ名をキーにして並べます。
  2. 2リモートに繋ぐなら type と url。
  3. 3手元でプロセスを起動するなら command と args。
  4. 4${DB_URL} のように環境変数を展開できます。鍵そのものを書かずに済むので、このファイルをリポジトリに入れられるのがポイントです。

3つのスコープ ─ 誰に見えるか

同名で重複したら local > project > user の順で勝つ local（既定）　自分だけ・そのプロジェクトだけ　→ ~/.claude.json
project　チーム全員　→ .mcp.json（バージョン管理に入れる）
user　自分だけ・全プロジェクト　→ ~/.claude.json
誤解「.mcp.json に書けば、黙ってすぐ使われる」 実際は対話セッションでは初回に承認を求められます。他人のリポジトリを開いた瞬間に勝手に繋がらないための仕組みです。

ポイント「チーム全員が同じツールを使えるようにしたい」の答えが .mcp.json（project スコープ）。個人の実験は local。設定ファイルの置き場所＝共有範囲という読み方は、Domain 3 の CLAUDE.md や settings.json とまったく同じです。

セクション

権限と副作用

確率的に動くものに、取り消せない操作をそのまま任せない。ここが安全設計の中心です。

図の読み方

  1. 1左（緑）が読む操作。検索・一覧・閲覧。副作用がないので自動実行してよい領域です。確認を挟むとむしろ邪魔になります。
  2. 2右（赤）が変える操作。返金・削除・送信・デプロイ。前に関門を置きます。
  3. 3境目は「間違えたとき、やり直せるか」です。やり直せるなら左、やり直せないなら右。
  4. 4下の一文が肝心なところ。関門はプロンプトでお願いするのではなく、コードで通れなくします。

たとえるなら

新人にどこまで鍵を渡すかという話です。資料の閲覧は自由にさせてよい。しかし押印は上長の確認を挟み、金庫の鍵はそもそも渡さない。

強い対策と弱い対策 弱い：system に「10万円を超える返金は実行しないでください」と書く
→ 守られる確率が高いだけで、破られることがある

強い：返金ツールの実行前に、コードで金額を検査して弾く
→ 通れないので、破りようがない
誤解「プロンプトで禁止しておけば安全」 実際はプロンプトは確率的な仕組みです。取り返しのつかない操作は、実行経路そのものを塞ぎます。

ポイント「system に "勝手に返金しないで" と書く」は弱い対策。実行経路そのものを塞ぐのが強い対策。
