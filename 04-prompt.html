セクション

system / user / assistant

メッセージには役割があり、効き方が違います。system は会話の全期間にわたって効きます。

図の読み方

  1. 1一番上の帯が system。幅が全体に広がっているのは、会話の間ずっと効き続けるという意味です。ただし「1回送れば覚えている」のではありません。毎回のリクエストに、そのまま入って送られています（前提編）。
  2. 2左下が user。その回の依頼やデータで、毎ターン追加されていきます。
  3. 3右下が assistant。Claude の応答で、これも履歴として残ります。
  4. 4一番下の帯が使い分けの原則。ふるまいを直したいときに触るのは system です。

ポイント役割の使い分けを誤ると、指示が薄まる。恒久ルールは system、可変の入力は user。

system の値は変えられるのか

その前に ─ system は「messages の中の1つ」ではない

リクエストの形を見ると分かります（Domain 1「実物を見る① 送るもの」）。system は messages 配列の外側にある、リクエストのトップレベルのフィールドです。messages に並ぶのは user と assistant。

同じ一文を「system に書くか、user の本文に混ぜるか」は選べますが、role の値を書き換えて行き来させるようなものではありません。入れ物が違う、というのが正確なところです。

system の値は変えられるのか

変えられます。system は毎回のリクエストに入れるフィールドなので、会話の途中で別の内容を送っても動きます。ただし実務では固定して使うのが普通です。理由は2つあります。

・キャッシュが全部無効になる　キャッシュは「ツール定義 → system → 会話」の順に積まれています。system を書き換えると、その後ろの会話ぶんもまとめて作り直しになります（前提編）。
・前提が食い違う　途中でルールが変わると、前半の応答と後半の応答が別の前提で書かれた状態になります。あとから読み返したときに、なぜその答えになったのか追えなくなります。

日付やユーザー名のように毎回変わる情報は、system ではなく user 側（末尾）に置くのが定石です。役割そのものを切り替えたいときは、system を書き換えるより別のセッションや子エージェントに分けるほうが素直です（Domain 1）。

同じ内容でも、置き場所で結果が変わる ✗ 毎ターンの末尾に「返金額は約束しないでください」→ 書き忘れた回に破られる。毎回トークンも食う
○ system に1回だけ書く → 全ターンに効く。会話が長くなっても消えない
誤解「system に書けば絶対に守られる」 実際は強く効きますが、あくまで確率的です。絶対に守らせたいことは、権限設定やコードで塞ぎます（Domain 2・Domain 5）。

ポイント役割の使い分けを誤ると、指示が薄まる。恒久ルールは system、可変の入力は user。

セクション

並べる順番

長い資料は先、指示は後ろ。最後に読んだ指示ほど、出力に強く効きます。

図の読み方

  1. 1左の①〜⑤が、プロンプトに置く順番です。役割 → 長い資料 → 例 → 指示 → 出力形式。
  2. 2中央の縦矢印が読む順。下に行くほど効きが強くなります。だから指示を後ろに置きます。
  3. 3右のパネルが効きやすくする3つ。とくに1つ目のタグで囲うのは、資料と指示の境界をはっきりさせるためです。
境界をはっきりさせる 資料をそのまま貼ると、どこまでが資料でどこからが指示か曖昧になります。
<document> …資料… </document> のようにタグで囲うと、「ここは読む対象であって指示ではない」と伝わります。

この順番は、前提編のプロンプトキャッシュとも一致します。変わらない資料が前、変わる指示が後ろ。精度の話とコストの話が、たまたま同じ結論になっています。

ポイント長い資料は前、指示と出力形式は後ろ。中身を変えず並べ替えるだけでも、指示の通りはよくなる。

セクション

考えさせる ─ thinking

難しい問題は「考える場所」を与える

結論だけをいきなり出させると精度が落ちます。推論の過程を出力させると、そのトークン列自体が次の判断材料になります。

図の読み方

  1. 1上（赤）がいきなり結論。質問と結論の間に何もありません。
  2. 2下（緑）は、質問と結論の間に thinking の箱があります。ここで条件を並べ、順に確かめています。
  3. 3効く理由は前提編にあります。出力は直前までの文章を手がかりに1トークンずつ選ばれるので、途中の思考を書き出すこと自体が、次を選ぶ手がかりを増やします。
  4. 4下の注記のとおり、思考も出力トークンです。そのぶん遅く、高くなります。
使いどころを分ける ○ 規約の条件を突き合わせて可否を決める、原因を切り分ける → 考えさせる
✗ 問い合わせを5種類に分類する、日付の書式を直す → 考えさせない。思考も出力トークンなので、そのぶん遅く高くなるだけ

ポイント「難しい判断＝考えさせる」「機械的な変換＝考えさせない」。使いどころを分けるのが設計。

「thinking」は2つの意味で使われる

上の図にあった thinking を、もう少し正確に分けておきます。似ていますが、片方はただのプロンプト、もう片方はAPIの機能です。

同じ「考えさせる」でも2種類ある ① プロンプトで考えさせる（chain-of-thought）
「順を追って考えてから答えて」と書くだけ。推論はふつうのテキスト出力の中に混ざって出てきます。APIの機能ではありません。

② 拡張思考（extended thinking）
リクエストに thinking フィールドを付けます。推論が専用のブロックとして分かれて返ってきます。

効く理屈は、どちらも同じ

出力は直前までの文章を手がかりに1トークンずつ選ばれます（前提編）。だから途中の推論を書き出すこと自体が、次を選ぶ手がかりを増やします。①と②の違いは「どこに出るか」であって、効き方の原理ではありません。

誤解「thinking を有効にすれば、タダで賢くなる」 実際は①も②も、思考ぶんが出力トークンとして課金されます。遅くなり、高くなります。だから使いどころを分けるのが設計です。

ポイント「考えさせる」には、プロンプトで書かせる方法とAPIの thinking を使う方法がある。効く理屈は同じで、どちらも出力トークンを食う。

実物を見る ─ 拡張思考のリクエストと応答

上の②を、実際の JSON で確認します。

リクエスト

{
  "thinking": { "type": "enabled", "budget_tokens": 10000 },1
  "max_tokens": 16000,2
  "messages": [ … ]
}

応答

"content": [
  { "type": "thinking", "thinking": "…条件を並べて順に確かめる…" },3
  { "type": "text", "text": "結論は…" }
]
  1. 1付けるのはこれだけ。「どう考えるか」を書く必要はありません。予算の最小は1024トークン。
  2. 2思考は出力の一部なので、budget_tokens は max_tokens より小さくします。
  3. 3content に thinking ブロックが増えます。中身は要約された思考で、内部の全文が出るわけではありません。
  4. 4この thinking ブロックの分も出力トークンとして課金されます。

ポイント付けるのは thinking フィールドだけ。応答に thinking ブロックが増え、そのぶん出力トークンを食う。

thinking の最中、アプリには何が届いているのか

ストリーミングを使うかどうかで、答えが正反対になります。

図の読み方

  1. 1①が stream なし。リクエストを送ったあと、モデルが思考を書いている間、アプリには何も届きません。完成してから content も stop_reason もまとめて1回で返ります。
  2. 2②が stream: true。思考は thinking_delta として少しずつ届きます。アプリの画面で「考えています…」の中身が流れて見えるのは、これです。ご想像のとおり、送られています。
  3. 3ただし流れるのは一方向だけです。アプリが途中で何かを返すことはありません。往復は1回のままで、変わっているのは「届き方」だけ。1回の応答を細切れに受け取っているだけなので、呼び出し回数もトークン数も変わりません。
  4. 4順番は決まっています。message_start →（ブロックごとに）content_block_start → delta の繰り返し → content_block_stop → 最後に message_delta → message_stop。
  5. 5いちばん大事なのがstop_reason がどこで来るか。最後の message_delta です。つまりストリーミングでも、アプリが分岐できるのは最後。途中の delta を見て「もう答えが出た」と判断することはできません（Domain 1「stop_reason で分岐」）。

ポイントthinking 中に届くのは、stream: true のときだけ。しかも一方向で、往復は増えない。stop_reason が来るのは最後の message_delta。

※ thinking ブロックの最後には signature_delta（署名）が届き、その直後に content_block_stop になります。この署名は、上で触れた「thinking ブロックをそのまま履歴に戻す」ときの検証に使われるものです。

理解度チェック ─ 基本

3問。

セクション

基準を明示する / ゼロ件を許す

「探して」ではなく「これに該当するものだけ」

基準を書かないと、モデルは広く拾います。増えるのは誤検知です。

図の読み方

  1. 1左は基準を書いていない場合。「バグ」の範囲が決まっていないので、気になった点をすべて拾ってきます。
  2. 2結果として誤検知（false positive）が増えます。件数は多いのに、確認の手間ばかりかかる状態です。
  3. 3右は該当条件を列挙したもの。①②③のどれかに当てはまるものだけを拾わせます。
  4. 4さらに「該当なしなら『なし』と答える」と書いてあるのが効きます。このすぐ下で扱います。
基準の書き方の型 ・該当するものを列挙する（できれば3つ以内）
・該当しないものも書く（「読みにくさ・命名は対象外」）
・境界を示す（「テストコード内は対象外」）
「よくない例を挙げるな」ではなく「これに当てはまるものを挙げよ」と書くのが要点です。
誤解「たくさん見つけてくれるほうが安全」 実際は誤検知が多いと人が確認しなくなり、結果として本物も見逃されます。精度が落ちれば、その仕組み自体が使われなくなります。

ポイント「見つけて」は基準ではない。何を該当とし、何を対象外とするかを書いて初めて、出力が絞れる。

ゼロ件を返せるようにする

モデルは何かを答えようとします。空を返してよいと明示しないと、無理に何かを作ります。

3つの受け皿は、それぞれ何を防ぐか

  1. 1findings: [] ── 0件を0件として受け取れるようにします。これがないと、モデルは空の出力を避けようとして、問題のないコードにも指摘を作ります（図の左）。
  2. 2confidence ── 確度を一緒に返させると、低いものだけ人が見るという運用ができます。全件を人が確認する必要がなくなります（Domain 5 の人間レビュー設計）。
  3. 3category: "その他" ＋ detail ── 3つのうち、いちばん効きます。用意した分類に収まらない入力が来たとき、逃げ道がないと必ずどこかに誤分類されます。自由記述の detail をセットにするのは、あとで「その他」の中身を見直せるようにするためです。

3つに共通しているのは、「答えられない」を答えとして表せる形にしてあることです。表せない受け皿を渡すと、モデルは無理にでも埋めます。

設問での問われ方 「分類させると、どれにも当てはまらないものが無理に分類される」
→ enum に「その他」を加え、detail の自由記述をセットにする。
「確認の手間を減らしたい」→ 確度を返させ、低いものだけ人が見る（Domain 5 の人間レビュー設計につながります）。

ポイントゼロ件・分類不能・確信が持てない ── これらを表現できる受け皿を先に用意する。

セクション

few-shot ─ 例を見せる

説明を増やすより、例を1つ見せる

出力の形や粒度は、言葉で説明するより実物を見せたほうが速く伝わります。

図の読み方

  1. 1「説明を厚くする」（左・赤）── 条件を言葉で積み上げるやり方。指定が増えるほど、どれかが抜けます。しかもどれが抜けたかは、出力を見るまで分かりません。
  2. 2「例を1つ見せる」（右・緑）── 入力と出力を対で1つ置くだけ。左のような条件はひとつも書いていません。
  3. 3「例が伝えるもの」（下）── その1つが同時に伝えている中身の内訳です。形式・粒度・語調。これらを言葉で全部書き出そうとすると、左の問題が起きます。
  4. 4例は入力とセットで示すのが要点です。出力だけ見せても「どんなときにその形にするのか」が伝わりません。
誤解「例は多いほどよい」 実際は例もコンテキストを消費します。効くのは最初の1〜3個で、そこから先は伸びが鈍ります。数より、下で扱う選び方です。

ポイント曖昧な依頼を長文で補うより、実物を1つ。ただし入力と出力を対で示す。

例は「難しいところ」から選ぶ

いちばん典型的な例を並べても、判断に迷う場面では効きません。

図の読み方

  1. 1「典型例ばかり」（左）── もともと迷わない場面にしか効きません。例を足したのに精度が上がらないときは、たいていこれです。
  2. 2「境界の例」（中央）── 「ここまでは該当、ここからは該当しない」という線を、例で引きます。言葉で線を引くより速く伝わります。
  3. 3「誤りの例」（右）── 理由と対で示すと、避けるべき方向が伝わります。
  4. 4「3つの決まりごと」（下）── とくに③。実際に間違えた出力を例に昇格させるのが、いちばん効率のよい増やし方です。探す手間がなく、必ず境界の例になっているからです。
Domain 3 とのつながり ③は、Domain 3 の「反復的な改善」と同じ考え方です。気づいた基準を会話で終わらせず、例として書き戻す。次回から自動で効きます。

ポイント例の価値は数ではなくどこを示すか。境界と誤りを見せると、判断が安定する。

セクション

構造化出力と tool_choice

JSONは「お願い」ではなく「型」で受け取る

文章で「JSONで返して」と頼むと、前置きや揺れが混ざります。スキーマ（ツール定義）で受け取れば、形が保証されます。

図の読み方

  1. 1左（赤）が文章でお願いした場合。上が指示、下が返ってきたものです。
  2. 2返ってきたほうをよく見てください。前置きの一文、コードブロックの囲み、そして "1,200円" という文字列が混ざっています。数値として扱えません。
  3. 3右（緑）がスキーマで受け取った場合。上が定義、下が結果です。
  4. 4こちらは型と必須項目が守られ、金額が整数で返っています。囲みも前置きもありません。

スキーマで受け取るというのは、記入欄の形を先に決めておくということです。書き方が割れる余地をなくします。ここでいうスキーマは、ツール定義の input_schema そのものです（Domain 2「ツール定義の解剖」）。抽出したい形をツールの引数として定義し、そのツールを呼ばせることで、受け皿を先に用意します。

決めておくべきこと ・型（金額は文字列か整数か）
・必須かどうか（required）
・値が見つからなかったときどう書くか（null を許すのか、空文字か、そもそも項目を出さないのか）
最後のひとつを決め忘れると、実運用でいちばん揉めます。
誤解「うまく指示すればきれいな JSON が返る」 実際は返ることも多いですが、保証されません。前置き、コードブロックの囲み、全角記号。構造化抽出はプロンプトの問題ではなくスキーマ設計の問題です。

ポイント構造化データ抽出は、プロンプトを工夫する問題ではなく、スキーマを設計する問題。値が無い場合の表現（null を許すか）まで決めておく。

ツールを「使わせる」4つの指定

tool_choice は、道具を使うかどうかの判断をこちらが決めるためのものです。

図の読み方

  1. 1auto ─ 既定値。使うかどうかをモデルが判断します。ふつうの道具はこれ。
  2. 2any ─ どれかは必ず使う。ただしどれを使うかはモデルが選びます。
  3. 3tool ─ この道具を必ず使う。名前で指定します。構造化出力を強制したいときはこれです。
  4. 4none ─ 道具を使わせません。道具を渡したまま、今回だけ文章で答えさせたいときに使います。
  5. 5下の注意が実務で効きます。any や tool を指定すると、前置きの文章が出なくなります。「先に説明してから」と書いても効きません。
設問での問われ方 「請求書から項目を抽出したい。必ずJSONで受け取りたい」→ tool_choice を tool にして抽出用ツールを指定。
「道具は渡しておくが、今回は使わせたくない」→ none。ツール定義を外す必要はありません。

ポイント「JSONで返して」と頼むのではなく、ツールを使わざるを得なくする。これが構造化出力の強制。

受け皿の形で、揺れを潰す

スキーマは「形を決める」だけでなく、迷ったときの逃げ道まで決めるものです。

図の読み方

  1. 1型を絞る。金額を integer にすれば、"1,200円" のような文字列は入りません。
  2. 2enum で選択肢を閉じる。自由記述にすると「円 / JPY / 日本円」のように表記が割れます。
  3. 3null を許す。読み取れなかった項目を「無い」と表せないと、それらしい値を作られます。
  4. 4「その他」＋ detail。用意した分類に収まらない入力の逃げ道です。これが無いと、近い分類へ無理に押し込まれます。
  5. 5required で必ず埋まるべき項目を宣言します。逆に言えば、埋まらないことがある項目は required に入れません。
さらに厳密にしたいとき ツール定義に strict: true を付けると、入力がスキーマに厳密に従うことを保証できます。
tool_choice: any と組み合わせると、「どれかのツールが必ず呼ばれ、かつ入力がスキーマどおり」という状態を作れます。

ポイントスキーマ設計とは、正常系の形と異常系の逃げ道を両方決めること。後者を忘れると運用で破綻する。

セクション

検証と再試行

出力が正しいかは、モデルに聞かない

「合っていますか」と尋ねても、返ってくるのはやはり確率的な答えです。検算はモデルの外側で行います。

図の読み方

  1. 1左がモデルの出力。ここが検査の対象です。
  2. 2中央の3つが、順に通す検査。①形（スキーマ・必須項目）、②中身（合計が合うか、元資料と一致するか）、③回帰（答えが分かっている過去の例）。
  3. 3右上が通れば採用、右下がだめなら差し戻し。
  4. 4差し戻しの点線は、理由を付けて、もう一度出力させる経路です。
  5. 5右端の注記が要点。①②はコードで書けるので、判定が毎回同じになります。ここが「検証」と呼べる条件です。
3段の使い分け ① 形：スキーマ検証。必須項目があるか、型は合っているか → コードで書ける
② 中身：明細の合計と請求書の総額が一致するか、元資料に同じ文字列があるか → コードで書ける
③ 回帰：答えが分かっている過去の例をまとめて流し、以前より悪くなっていないか見る → プロンプトや設定を変えたときに効く
誤解「もう1体の Claude にチェックさせれば検証になる」 実際は参考にはなりますが、判定が毎回同じになる保証がありません。補助であって、決定的な検証の代わりにはなりません。

ポイント「もう一度Claudeに確認させる」は検証ではない。判定が毎回同じになる方法だけが検証になる。

検証に落ちたら、理由を付けて返す

検証は通すか落とすかで終わりではありません。落ちた理由を渡して、もう一度書かせます。

図の読み方

  1. 1出力を検証にかけます（形＝スキーマ、中身＝合計や元資料との照合）。
  2. 2通れば採用。落ちたら捨てるのではなく差し戻します。
  3. 3差し戻すときは「何が」「どう違ったか」を具体的に書きます。「不正です」だけでは同じ間違いを繰り返します。
  4. 4差し戻しは同じ会話に足して送ります。前の出力と指摘が履歴に残るので、次はそこを避けられます。
  5. 5再試行の上限は必ず置きます。通らない入力は存在するので、2〜3回で人へ回すか、その1件を落とします。
誤解「落ちたら同じプロンプトでもう一度投げればいい」 実際は同じ入力を投げ直しても同じ理由で落ちる確率が高い。指摘を入力に足すことが再試行の本体です。

ポイント検証の出口は3つ ── 採用・差し戻し・打ち切り。差し戻しには必ず理由を、打ち切りには必ず上限を。

バッチ処理

急がない大量処理は、まとめて投げる

1件ずつ同期で投げる代わりに、まとめて非同期で処理します。料金が半分になります。

図の読み方

  1. 1上段が使い分け。「すぐ答えが要るか」だけが判断基準です。要らないならバッチ。
  2. 2料金は半額。入力・出力の両方に効きます。大量処理では効果が大きい。
  3. 3多くは1時間以内に終わりますが、保証は24時間。それを超えた分は期限切れになります（課金されません）。
  4. 41バッチの上限は10万件または256MB。先に達したほうが効きます。
  5. 5結果は29日間取得できます。それ以降はバッチ自体は見えても、結果は取り出せません。
向く仕事 大量の評価セットの実行 ／ 投稿の一括分類・モデレーション ／ 蓄積した文書からの一括抽出 ／ 過去データの棚卸し
いずれも「今すぐ答えが要らない」点が共通です。

ポイント判断基準はひとつ ── すぐ答えが要るか。要らないなら、半額で通せる。

順序は保証されない ─ custom_id で対応づける

結果は投げた順に返ってきません。1件ごとに付けた ID で突き合わせます。

図の読み方

  1. 1送るとき、1件ごとに custom_id を付けます。英数字・ハイフン・下線で64文字までです。
  2. 2結果の順序は保証されません。投げた順に返る前提で書くと、静かに取り違えます。
  3. 3だから必ず custom_id で突き合わせます。意味のあるIDにしておくと、突き合わせも調査も楽になります。
  4. 4結果は4種類。成功以外の3つは課金されません。expired は24時間で処理しきれなかったものです。
できないこと stream: true は使えません（結果はまとめて1つのファイルで返るため）。
一方でツール使用・複数ターンの会話・拡張思考・画像は使えます。「バッチだから単発の質問しか投げられない」わけではありません。
※ 処理に時間がかかるため、共通の長いプロンプトを使うならキャッシュは長め（1時間）の設定と相性が良くなります。

ポイント順序は保証されない ── これがバッチ処理で最初に踏む落とし穴。ID で対応づけるのが唯一の正解。

多重レビュー

1回の判定を信じない構成

見落としが致命的な場面では、同じ入力を複数回・複数の観点で通します。

図の読み方

  1. 1左がmulti-instance。同じ入力を別々の観点で並行して見せ、結果を突き合わせます。
  2. 2観点を変えるのが要点です。同じ指示を3回投げても、同じ見落としをします。安全性・性能・仕様のように違う目を当てます。
  3. 3右がmulti-pass。段階で役割を変えます。1回目は広く拾い、2回目で1件ずつ潰す。
  4. 4この分業が効くのは、「広く挙げる」と「厳しく絞る」を同時にやらせると両方中途半端になるからです。Task 4.1 の基準の話と裏表です。
組み合わせる 1回目で候補を広く挙げ（再現率を優先）、2回目で1件ずつ「本当に該当するか」を検証する（適合率を優先）。
2回目は1件が1リクエストになるので、件数が多いならバッチ処理と相性が良いです（Task 4.5）。

ポイント横に並べる＝観点を変える。縦に重ねる＝役割を変える。どちらも「1回の判定を信じない」ための構成。

倍のコストを払う価値があるか

多重レビューは回数ぶん確実に高くなります。使いどころを絞る必要があります。

図の読み方

  1. 1「多重にする価値がある」（左）── 共通するのは見落としのコストが、追加の実行コストより大きいことです。この一文が判断基準になります。
  2. 2「やりすぎ」（右）── とくに「同じ指示をただ繰り返す」は効果が薄い ── 同じ見落としが3回起きるだけです。観点を変えなければ重ねる意味がありません。
  3. 3「安く重ねる工夫」（下）── 2回目以降の対象を絞るのが最も効きます。全件を2回通す必要はありません。
  4. 4急がない検証パスはバッチに回せば半額です。多重レビューとバッチは組み合わせやすい。
誤解「多重にすれば精度が上がる」 実際は上がるのは観点や役割を変えたときだけ。同じ指示の繰り返しは、コストだけが倍になります。

ポイント多重化の判断は「精度が上がるか」ではなく「見落としのコストが実行コストを上回るか」。
