セクション

CLAUDE.md の階層と読み込まれ方

CLAUDE.md は4つの場所に置ける

置く場所によって「誰に効くか」が変わります。まずこの4段を覚えます。

図の読み方

  1. 1管理ポリシーは組織のIT部門が置くもので、利用者側で無効化できません。企業導入の設問で出ます。
  2. 2ユーザー（~/.claude/CLAUDE.md）は自分の全プロジェクトに効きます。個人の好みはここ。
  3. 3プロジェクト（./CLAUDE.md）はチーム共有。git にコミットするのがここです。
  4. 4サブディレクトリに置くと、そのディレクトリを扱うときだけ読み込まれます。モノレポで効きます。
  5. 5CLAUDE.local.md は同じ場所に置く個人用。自動で .gitignore に入るので、共有されません。
誤解「上位の CLAUDE.md があると、下位は無視される」 実際は上書きではなく、すべて連結されます（このすぐ下）。競合したときの扱いは、書いた内容しだいです。

ポイント「誰に効かせたいか」で置き場所が決まる。組織全員＝管理ポリシー、自分だけ＝ユーザー、チーム＝プロジェクト、自分＋このリポジトリだけ＝CLAUDE.local.md。

上書きではなく、順に足していく

ルートから作業ディレクトリへ向かって走査され、見つかったものが全部つながります。

図の読み方

  1. 1走査はルート側から作業ディレクトリへ向かって行われます。
  2. 2各階層で CLAUDE.md → CLAUDE.local.md の順に読まれます。
  3. 3結果は連結。上位が下位に置き換わるのではなく、全部が並んでコンテキストに載ります。
  4. 4サブディレクトリのものだけは例外で、そのディレクトリを実際に読むときに追加されます。
設問での問われ方 「モノレポで、パッケージごとに違う規約を適用したい」→ 各パッケージに CLAUDE.md を置く（全部をルートの1枚に詰め込まない）。
理由は2つ：関係ないパッケージの規約を読ませずに済む／ルートの1枚が肥大化しない。

ポイント合成であって上書きではない。だから「置けば置くほど効く」のではなく「置いた分だけ窓を食う」。

セクション

@import で分割する

CLAUDE.md が長くなったら、テーマごとに分けて読み込みます。

図の読み方

  1. 1左が本体。行頭に @パス と書くだけで、その中身がそこに展開されます。
  2. 2相対パス・絶対パス・~/ の3通りが使えます。相対パスは、その行を書いたファイルから見た位置です。
  3. 3入れ子は4段まで。import した先がさらに import しても、4ホップで止まります。
  4. 4コードスパン（バッククォート）やコードブロックの中の @ は展開されません。
設問での問われ方 「CLAUDE.md が肥大化して読みにくい。どう整理するか」→ テーマごとにファイルを分け、@import で束ねる。
「個人の好みをチームに押し付けずに読み込みたい」→ @~/.claude/my-rules.md のようにホーム側を import する、または CLAUDE.local.md を使う。

ポイント@import は「分割して見通しを良くする」ための道具。展開後は結局1つにつながるので、合計の量は減らない。

スラッシュコマンドとスキル

スラッシュコマンド ─ 1ファイル＝1コマンド

よく使う手順を .claude/commands/ に置くと、/名前 で呼び出せます。

図の読み方

  1. 1ファイル名がコマンド名になります。deploy.md なら /deploy。
  2. 2先頭の YAML frontmatter で3つ指定できます。allowed-tools はそのコマンド実行中だけツールを絞るもので、権限設計としても使えます。
  3. 3本文の中に $ARGUMENTS や $1 と書いておくと、呼び出し時の引数が入ります。
  4. 4置き場所はプロジェクト（.claude/commands/）と個人（~/.claude/commands/）の2通り。前者はチームで共有されます。
サブディレクトリで名前空間を作れる .claude/commands/db/migrate.md のように掘ると、コマンドが整理されます。数が増えたときに効きます。

ポイント「毎回同じ順番でやってほしい手順」の置き場所。CLAUDE.md（常に効く）と違い、呼んだときだけ効く。

スキル ─ ディレクトリごと束ねる

補助ファイルを伴う手順や、別コンテキストで走らせたい作業はスキルにします。

図の読み方

  1. 1スキルはディレクトリです。SKILL.md が本体で、チェックリストや例などの補助ファイルを同梱できます。ここがコマンドとの一番の違い。
  2. 2description はClaudeが自動で使うかどうかの判断材料。ツールの description と同じ役割です。
  3. 3context: fork を付けると、別コンテキストのサブエージェントとして走ります。大量に読む作業を、親の窓を汚さずに任せられます。
  4. 4ただし fork した先は親の会話も CLAUDE.md も引き継ぎません。必要な前提は指示に書いて渡す必要があります。
誤解「fork すれば速くなる・賢くなる」 実際は目的はコンテキストの隔離です。引き継がれないことが利点であり、同時に渡し忘れの原因にもなります。

ポイント補助ファイルが要る、または別コンテキストで走らせたい → スキル。単発の手順書 → スラッシュコマンド。

CLAUDE.md / コマンド / スキル の使い分け

「何を繰り返したいか」で置き場所が決まります。設問はここを突いてきます。

判断の順序

  1. 1いつも効いていてほしいか？ → はい なら CLAUDE.md。会話のたびに載るので、短く保つ。
  2. 2呼んだときだけでよいか？ → 単発の手順ならスラッシュコマンド。
  3. 3補助ファイルが要る／別コンテキストで走らせたいか？ → スキル。
  4. 4そもそもモデルの判断が要らないか？ → それは hooks の領域です（Domain 1）。「編集したら必ず整形」のような処理は、ここに書くべきではありません。
設問での問われ方 「毎回同じ注意を書いている」→ CLAUDE.md／「リリース手順を毎回説明している」→ スラッシュコマンド／「レビュー観点と参考資料をセットで使い回したい」→ スキル／「編集後に必ずリンタを走らせたい」→ hooks。

ポイント4つの選択肢を「常に効く／呼んだとき／束ねたい／判断不要」で切り分ける。この分類がそのまま設問の選択肢になる。

パス固有ルール

.claude/rules/ に置き、frontmatter で対象パスを指定します。

図の読み方

  1. 1左上がルールファイルの中身。frontmatter の paths: にグロブを並べるだけです。
  2. 2「いつ読まれるか」 ── ここが CLAUDE.md との違いです。paths を書けばそのファイルを扱うときだけ、書かなければ常に窓に載ります。関係ない規約でウィンドウを埋めないための仕掛けです。
  3. 3「こう書ける」 ── 複数パターンと {ts,tsx} のブレース展開。1ファイルで複数の拡張子をまとめられます。
  4. 4「サブディレクトリも掘れる」 ── 分けて置いても自動で拾われるので、規約の種類が増えても1ファイルが肥大しません。
CLAUDE.md との使い分け 常に効かせたい規約（言語共通の方針）→ CLAUDE.md
特定の種類のファイルにだけ効かせたい規約（Reactコンポーネントの書き方、テストの命名）→ .claude/rules/ ＋ paths
後者を CLAUDE.md に全部書くと、関係ない作業のときも窓を食い続けます。

ポイントpaths は「いつ読ませるか」のスイッチ。規約が増えたときに、窓を守りながら増やせる仕組み。

セクション

plan mode と直接実行

plan mode では、調べることはできますが変更はできません。まず計画を出させて、承認してから実行に移します。

図の読み方

  1. 1左が plan mode。読む・調べるはできて、変えるはできません。この制約が本質です。
  2. 2成果物は変更計画。人はそれを見て、方針の段階で了承／却下できます。
  3. 3右が直接実行。速い代わりに、方針の誤りに気づくのが「実行後」になります。
  4. 4承認の位置が違うのがこの2つの差です。計画に対して1回か、操作ごとに何度もか。
どちらを選ぶか plan mode 向き：影響範囲が読めない変更、未知のコードベース、後戻りが高くつく作業、方針を人と合意したい場面
直接実行 向き：やることが決まっている小さな修正、間違えてもすぐ戻せる作業
起動は --permission-mode plan、対話中は Shift+Tab でも切り替えられます。
誤解「plan mode は安全だから常に使えばよい」 実際は小さな確実な修正にまで計画の往復を挟むと、単に遅くなります。後戻りのコストが高いときの道具です。

ポイントplan mode の本質は「編集ができない」こと。だから、方針を間違えたまま手が動く事故を構造的に防げる。

セクション

反復的な改善

出力が確率的である以上、一発勝負は分が悪い。小さく回して、そのつど基準を書き足していきます。

図の読み方

  1. 1左は長い指示を1回で書くやり方。成果物が大きいので、どこがずれたのか切り分けられません。
  2. 2右は小さく頼んで、結果を見て、ずれた点を基準として書き足すループです。
  3. 3肝は最後の矢印です。気づいた基準をその場の会話で言うだけにせず、CLAUDE.md やコマンドに残す。そうすると次回から自動で効きます。
  4. 4これは第4章（プロンプト）の「例を1つ見せる」とも繋がります。ずれた出力そのものが、次の基準の材料になります。
設問での問われ方 「生成されるコードが毎回チームの規約から外れる。どうするか」
→ その場で指摘し直すのではなく、規約を CLAUDE.md に書いて次回以降に効かせる。
「大きな機能を一度に作らせたらうまくいかない」→ plan mode で方針を合意 → 小さい単位に分けて実行 → 都度確認。

ポイント改善を会話の中で終わらせない。設定ファイルに書き戻して初めて、次回から効く。

セクション

非対話実行と CI/CD

人がいない場所で走らせる ─ claude -p

対話せずに1発で実行し、結果を標準出力へ、合否を終了コードで返します。

図の読み方

  1. 1-p（--print）を付けると非対話モード。承認ダイアログが出ないので、そのままスクリプトに乗せられます。
  2. 2結果は標準出力へ。合否は終了コードで返るので、CI のステップの成否として扱えます。
  3. 3--output-format json にすると、結果本文のほかにセッションIDや使用量が構造化されて返ります。後続処理で扱いやすくなります。
  4. 4さらに --json-schema で出力の形そのものを指定できます。Domain 4の「スキーマで受け取る」を、CLI の外側でやる形です。
つまずきやすい非対話では確認のダイアログを出せません。「危なければ人が止める」という設計が成立しないので、何を許すかを事前に決めておくのが前提になります（後述の settings.json と permissions）。

ポイント-p は「対話をやめる」だけでなく「人の承認をやめる」こと。権限設計とセットでなければ使えない。

承認できない場所では、事前に許可を決める

非対話実行では、許可の与え方が2通りあります。どちらを選ぶかが設問になります。

図の読み方

  1. 1「使うツールを列挙する」（左）── レビュー用途なら Read,Grep だけで足ります。書き込み系を渡さなければ、壊しようがありません。
  2. 2「全部許可する」（右）── 楽ですが、CI は人が見ていない場所なので、事故が起きても止まりません。設問では基本的に誤答側です。
  3. 3この2つの中間が plan（提案のみ）と acceptEdits（編集は自動、それ以外は確認）。「全部か、なしか」ではなく段階で選べるのが要点です。
  4. 4「GitHub Actions」（下）── 公式アクションを使い、APIキーはシークレットとして渡します。ワークフローのファイルに直接書いてはいけません。
設問での問われ方 「CI で自動コードレビューを走らせたい。権限はどう設定するか」
→ 読み取り系のツールだけを allowedTools で開ける。bypassPermissions は選ばない。
考え方は Domain 2 と同じです。やり直せる操作は自動、やり直せない操作は通さない。

ポイントCI は「承認する人がいない」場所。だから権限は実行前にすべて決まっていなければならない。

セクション

settings.json と permissions

設定ファイルはどこが優先されるか

同じ項目が複数の場所にあるとき、上にあるものが勝ちます。

図の読み方

  1. 1一番上が組織の管理設定。利用者側で上書きできません。CLAUDE.md の管理ポリシーと同じ考え方です。
  2. 2次が起動時のCLIフラグ。その場限りの指定が、ファイルより強く効きます。
  3. 3settings.local.json は自分専用。共有しない設定はここ。settings.json はチーム共有で git に入れます。
  4. 4一番弱いのがホームディレクトリの設定。自分の全プロジェクトに効く既定値です。ここで注意 ── 「個人に近いほど弱い」わけではありません。settings.local.json（自分だけ）は settings.json（チーム共有）より強いです。
CLAUDE.md との違い CLAUDE.md は連結（全部が足し合わされる）。settings.json は優先順位で決着（強いほうが勝つ）。
同じ「階層がある」でも扱いが違うので、設問で入れ替えられると間違えます。

ポイントCLAUDE.md＝足し算、settings.json＝勝ち負け。ここを混同しない。

allow / deny で通れる道を決める

ツール名とパターンの組で、許可と禁止を書きます。

図の読み方

  1. 1書式は ツール名(パターン)。Bash(npm test *) のように、コマンドの形まで絞れます。
  2. 2* でワイルドカード。Bash(npm run *) なら npm run で始まるものだけ通ります。
  3. 3allow は「確認なしで通す」。毎回聞かれると邪魔になる、やり直せる操作を並べます。
  4. 4deny は「通さない」。.env の読み取りや rm -rf のように、事故が致命的なものを塞ぎます。
  5. 5どちらにも該当しないものはその場で確認されます。だから deny を書くことに意味があります。
設問での問われ方 「秘密情報のファイルを絶対に読ませたくない」→ deny に Read(./.env)。CLAUDE.md に「読まないで」と書くのは弱い対策。
「テストは毎回自動で走らせたいが、いちいち確認されて煩わしい」→ allow に Bash(npm test *)。

ポイントプロンプトでのお願いは確率的、permissions は決定的。取り返しのつかない操作は必ず後者で塞ぐ。
