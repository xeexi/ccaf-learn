1-8　ループが壊れるとき

ゴール壊れ方3つと、最も単純な対処を選べる。

止まらない・道具が動かない・答えが途中で切れる。実装ミスの多くはこの3つで、どれも1周の4手のどこかが崩れた形です。直すのはモデルの側ではなく外側のコードです。

BLUEPRINT 1.1Design and implement agentic loops for autonomous task execution

壊れ方1周のどこが崩れているか最も単純な対処
① 終わらない
同じ手を延々と繰り返す		 手順4 →手順1 の戻りが止まらない。1周そのものは正しく回っているので、「もっと注意深く」と頼んでも直らない 反復上限を外側のコードに置く。「5周で打ち切る」と書くだけ
② 返し忘れ
会話の筋が通らなくなる		 手順4 で tool_use に対する tool_result を返していない。頼んだ仕事の結果が永久に来ない状態 id の対応を必ず取る。要求1つに結果1つを、機械的に突き合わせる
③ 窓が溢れる
最初の指示が効かなくなる		 手順4 で返す量が多すぎる。ログ5万行がそのまま履歴に積まれ、数周で窓が満杯になる ツール側で絞る。必要な行だけ返す（載せてから減らすより確実）

ポイント試験では「一番単純で効く対処」が正解になりやすい。まずは反復上限・結果の整合・返す情報量の3点を疑う。

試験でのねらわれ方 「エージェントが暴走している。最初に取るべき対処は？」という設問で、「より大きなモデルに変える」「アーキテクチャを作り直す」は誤答になりやすい選択肢です。反復上限のような、小さくて確実な手が正解になります。
ただし、反復上限は「保険」であって停止条件ではない 正常に終わるときの合図は stop_reason が end_turn になることです。 上限は「壊れたときに無限に回らないようにする」ためのもので、これを主な止め方に据えると、 まだ終わっていない仕事を途中で切ることになります ── 5周で足りる日もあれば12周かかる日もあるのが、確率で動く仕組みです。
設問で「ループはどう終わらせるか」と問われたら、答えは上限ではなく stop_reason。上限は別に置く安全弁です。
誤解「壊れているのはモデルの判断なので、プロンプトで丁寧に頼めば直る」 実際は3つともコードで決まる話です。設問で「プロンプトで丁寧に頼む」系の選択肢が並んでいたら、たいてい誤答です。
