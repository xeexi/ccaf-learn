1-14　前提は関門で、引き継ぎは欄で

お願いではなく、通れないようにする

「デプロイの前に必ずテストを通して」と文章で頼むと、急いだときに何回かは飛ばされます。順序を守らせたいなら、飛ばせない場所に置きます。

BLUEPRINT 1.4多段ワークフローの強制とハンドオフ

ゴールお願いと関門の違いを説明できる。

図の読み方

  1. 1検査はモデルがやる気になったときではなく、毎回同じ場所で走ります。順序が固定されるのはここです。
  2. 2関門が見ているのは結果だけです。モデルの説明や自己申告は見ません。だから「通したつもり」が起こりません。
  3. 3赤い戻りが重要です。ただ拒否すると、モデルは同じ手をもう一度試します。足りないものを返すと、次の一手が変わります。
  4. 4Claude Code では、ツール実行の前に走らせる PreToolUse で判定して止め、実行の後に必ずやりたい処理は PostToolUse に置きます（フック＝ツール実行の前後で自動的に走る仕組み。Domain 3・5）。

ポイント順序を守らせたいなら、通れない場所を作る。拒否するときは理由を返す。

引き継ぎは自由文にしない

子から親へ、あるいは次の担当へ渡す要約を自由文にすると、何が書かれていないかに誰も気づけません。

図の読み方

  1. 14つの欄は、次に動く側が最初に必要とするものだけです。経過や試行錯誤は入れません。
  2. 2欄が固定なので機械的に検査できます。自由文だと、書かれていないことは誰の目にも留まりません。
  3. 3続きを始められる側が読むのは票だけです。前の作業の履歴は残っていないので、票に書かれていない前提は失われます。
  4. 4同じ形にしておくと、前回の票と見比べるだけで何が進んだかが分かります。人が引き継ぐときにも同じ効き方をします。
誤解「引き継ぎは詳しいほどよい」 実際は長い引き継ぎは受け取る側の窓を埋め、しかもどこが重要か分からなくなります。欄を決めて短く書くほうが、渡し漏れも減ります。

ポイント前提は文章で頼まず通れなくする。引き継ぎは自由文でなく欄を決める。どちらも「守られるか」をモデルの判断から外す手。
