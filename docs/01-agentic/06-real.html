1-6　実物を見る ─ 往復のJSON

実物を見る ① こちらから送るもの

前の「誰が、何を送っているのか」のシーケンス図で、①（アプリ → Claude の青い矢印）にあたる中身です。細かく覚える必要はありません。

BLUEPRINT 1.1Design and implement agentic loops for autonomous task execution

ゴール1回のリクエストに何が入っているかを挙げられる。

1回目のリクエスト

{
  "model": "claude-opus-5",1
  "max_tokens": 1024,2
  "system": "あなたはこのリポジトリの案内役です。",3
  "tools": [4
    {
      "name": "search_files",
      "description": "ファイルの中身を検索する。答える前に必ず呼ぶ",
      "input_schema": { "type": "object",
        "properties": { "pattern": { "type": "string" } },
        "required": ["pattern"] } }
  ],   ← 変えなければ、ここまでは毎回同じ
  "messages": [5
    { "role": "user", "content": "TODO はどこに残ってる？" }
  ]
}
  1. 1どのモデルに聞くか。
  2. 2返事の長さの上限。達すると stop_reason が max_tokens になります。
  3. 3システム指示。会話の間ずっと効きます。
  4. 4ツールの定義。使わなくても窓を食うのがこれ。道具の数だけ毎回送られます。
  5. 5会話履歴。往復のたびに伸びるのはここだけです。
緑がかった色を付けた部分について こちらが変えない限り毎回そっくり同じになります。だからプロンプトキャッシュが効くのはそこまで（前提編「同じ前半は使い回せる」）。逆に言えば、ここは固定ではありません。tools を1つ足す、MCPサーバを繋ぐ、system を書き換える ── どれをやっても、そこから後ろは全部作り直しになります。

ポイント1回のリクエストに、指示・道具・会話が全部入っている。この全部が同じコンテキストウィンドウに載る。

綴りが決まっているもの／自分で決めるもの

紛らわしいので分けておきます。model system messages tools name description input_schema role content は API が決めた綴りで、変えられません。

一方 search_files という名前、その説明文、pattern という引数名はすべて自分で決めるものです。この教材に出てくる道具の名前は、説明のために私が作った架空のものです。

実物を見る ② 返ってくるもの

シーケンス図の ②（Claude → アプリ の橙の矢印） の中身です。

{
  "role": "assistant",
  "content": [1
    { "type": "text", "text": "確認しますね。" },
    { "type": "tool_use",2
      "id": "toolu_01A...",
      "name": "search_files",
      "input": { "pattern": "TODO" } }
  ],
  "stop_reason": "tool_use",3
  "usage": { "input_tokens": 412, "output_tokens": 68 }4
}
  1. 1前提編で見たブロックの配列に、text と tool_use が並んで入っています。喋りながら道具を頼めるということです。
  2. 2「この道具を、この引数で使いたい」という要求。検索はまだ走っていません。
  3. 3アプリが分岐に使うのはこの値だけ。上の文章では判断しません。
  4. 4使ったトークン数。キャッシュが効いた分も別項目で分かります。

ポイント道具を使いたいという要求は content の中に並ぶ。アプリが次の一手を決めるのに見るのは、その外側の stop_reason。

実物を見る ③ 返し直すもの

シーケンス図の ④と⑤ にあたります。ここでループが閉じます。

2回目のリクエスト

"messages": [
  { "role": "user", "content": "TODO はどこに残ってる？" },
  { "role": "assistant", "content": [ …さっきの tool_use をそのまま… ] },1
  { "role": "user", "content": [
      { "type": "tool_result",
        "tool_use_id": "toolu_01A...",2
        "content": "{\"hits\":3}" } ] }
]

最終の応答

{ "content": [ { "type": "text", "text": "TODO は3か所に残っています。" } ],
  "stop_reason": "end_turn"3 }
  1. 1前回の応答も、そのまま履歴に入れて送り返します。省くと、Claude は自分が何を頼んだのか分からなくなります。
  2. 2どの要求に対する結果かを id で対応づけます。ここがずれると会話が壊れます。
  3. 3言い切ったので end_turn。アプリはここでループを抜けます。

ここで気づいてほしいこと

2回目のリクエストには、1回目の中身が丸ごと含まれています。前提編の「毎回まるごと送り直す」が、ここで実物として確認できます。往復が増えるほど messages は長くなり、input_tokens も増えます。

図との対応 ① モデルが考える → 応答が生成される
② tool_use を返す → stop_reason: "tool_use"
③ アプリが実行する → JSON には現れない。あなたのコードの中の出来事
④ tool_result を返す → 2回目のリクエストの末尾
⑤ 答える → stop_reason: "end_turn"

ポイントループとは、この配列に1往復ぶん追記しては投げ直すこと。それ以上でも以下でもない。
