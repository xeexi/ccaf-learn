1-4　stop_reason で分岐する

ループを回すか止めるかは stop_reason が決める

ゴール分岐を stop_reason で書く理由を説明できる。

モデルからの応答には、なぜそこで止まったかが必ず付いてきます。アプリはその値を見て、次に何をするかを決めます。値を選んで確かめてください。

BLUEPRINT 1.1Design and implement agentic loops for autonomous task execution

▶ 返ってきた値を選ぶと、上の図の該当する行だけが残ります
pause_turn ── 「戻るのは tool_use だけ」と覚えると事故る web検索のように Anthropic 側で実行されるツール（Domain 2）を使うと、その実行はモデルの中で何周も回ります。 既定10周で一区切りが付き、pause_turn が返ります。まだ答えは出ていません。 こちらが実行するものは何もないので、返ってきた応答をそのまま履歴に足して、もう一度投げるだけで続きが進みます。 ここを完了として扱うと、検索の途中で会話が終わります。

ポイント「Claudeの返事を文字列で判定して分岐」はアンチパターン。分岐はこの構造化された値だけで決める ─ ここは確率ではなく、決定的に書ける部分。

値ごとの扱いと、よくある誤解

ゴール6つの値を「続ける／終わる／直す」に振り分けられる。

アプリ側の分岐は、これだけで書ける if stop_reason in ("tool_use", "pause_turn"): 会話に足して、もう一度投げる
elif stop_reason in ("end_turn", "stop_sequence"): 画面に表示して終わり
elif stop_reason in ("max_tokens", "model_context_window_exceeded"): 途中で切れている
elif stop_reason == "refusal": 別の経路へ
誤解「返事に『検索します』と書いてあったら検索すればいい」 実際は言い回しは毎回揺れます（「調べますね」「確認いたします」「Let me search」…）。揺れない値で分岐するのが鉄則です。
誤解「知らない値が返ってきたら、とりあえず完了として扱えばよい」 実際は③と④を完了として扱うと、尻切れの文章や、断られた事実がそのまま利用者に出ます。分岐に書いていない値は、完了ではなく異常として扱うのが安全です。
