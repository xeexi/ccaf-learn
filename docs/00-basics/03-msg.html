0-3　送っているものの形

ゴールmessages の形を読めて、content が2通りに書けることを言える。

毎回送り直している「会話まるごと」は、実際にはどんな形をしているのか。やり取りは JSON で、この形は最後まで変わりません。ここで掴んでおくと、以降に出てくる名前はどこに入るかだけで意味が取れます。

送るもの ─ ここまでの会話

"messages": [1
  { "role": "user",
    "content": "こんにちは" },2
  { "role": "assistant",
    "content": "どうも" },
  { "role": "user",
    "content": "続きを" }
]

返るもの ─ 1件ぶん

{
  "role": "assistant",
  "content": [3
    { "type": "text",
      "text": "では…" }
  ],
  "stop_reason": "end_turn"4
}
  1. 1履歴は配列です。〈会話は毎回、まるごと送り直している〉の「厚くなる紙の束」は、この配列が伸びること。
  2. 21件に入るのは role と content の2つだけ。role は user か assistant のどちらかです。
  3. 3返ってきた1件は、そのまま次回の末尾に足せます。送る形と返る形が同じなので、積むだけで会話になります。
  4. 4content の外側にも値が付きます。外側のものは次回に送り返しません（値の意味は Domain 1）。

ポイント会話の実体は {role, content} の配列。返ってきたものを末尾に足すだけで履歴になる。

content は「ブロック」の入れ物

ゴール返る側がいつも配列になる理由を言える。

同じ内容を2通りに書けます。送る側は短いほうで済みますが、返る側はいつも配列です。

短い書き方 ─ 送る側だけ

"content": "こんにちは"

ブロックの配列 ─ 返る側はこちら

"content": [
  { "type": "text",
    "text": "こんにちは" }
]

ポイント返ってくるのは文章ではなくブロックの列。中身が何かは type が決めるので、種類が増えても読み方は変わらない。

いまは text しか出てきませんが、type の種類はこの先で増えます ── 画像、道具を使いたいという要求、その結果。どれも同じ配列に並びます。「文章が返る」と覚えると、道具の話に入ったところで必ず躓きます。

誤解「JSON を書けるようにならないと理解できない」 実際は試験でコードは書きません。要るのはどの名前が何を指すかだけです。設問はこの語彙で書かれます。

※ 実際のリクエストには model などの指定も要ります。1回ぶんの全体は Domain 1「実物を見る」でまとめて見ます。
