4-2　system / user / assistant

メッセージには役割があり、効き方が違います。system は会話の全期間にわたって効きます。

ゴール恒久のルールと可変の入力を、書く場所で選び分けられる。

図の読み方

  1. 1一番上の帯が system。幅が全体に広がっているのは、会話の間ずっと効き続けるという意味です。ただし「1回送れば覚えている」のではありません。毎回のリクエストに、そのまま入って送られています（前提編）。
  2. 2左下が user。その回の依頼やデータで、毎ターン追加されていきます。
  3. 3右下が assistant。Claude の応答で、これも履歴として残ります。
  4. 4一番下の帯が使い分けの原則。ふるまいを直したいときに触るのは system です。

system の値は変えられるのか

その前に ─ system は「messages の中の1つ」ではない

リクエストの形を見ると分かります（Domain 1「実物を見る① 送るもの」）。system は messages 配列の外側にある、リクエストのトップレベルのフィールドです。messages に並ぶのは user と assistant。

同じ一文を「system に書くか、user の本文に混ぜるか」は選べますが、role の値を書き換えて行き来させるようなものではありません。入れ物が違う、というのが正確なところです。

system の値は変えられるのか

変えられます。system は毎回のリクエストに入れるフィールドなので、会話の途中で別の内容を送っても動きます。ただし実務では固定して使うのが普通です。理由は2つあります。

・キャッシュが全部無効になる　キャッシュは「ツール定義 → system → 会話」の順に積まれています。system を書き換えると、その後ろの会話ぶんもまとめて作り直しになります（前提編）。
・前提が食い違う　途中でルールが変わると、前半の応答と後半の応答が別の前提で書かれた状態になります。あとから読み返したときに、なぜその答えになったのか追えなくなります。

日付やユーザー名のように毎回変わる情報は、system ではなく user 側（末尾）に置くのが定石です。役割そのものを切り替えたいときは、system を書き換えるより別のセッションや子エージェントに分けるほうが素直です（Domain 1）。

同じ内容でも、置き場所で結果が変わる ✗ 毎ターンの末尾に「返金額は約束しないでください」→ 書き忘れた回に破られる。毎回トークンも食う
○ system に1回だけ書く → 全ターンに効く。会話が長くなっても消えない
誤解「system に書けば絶対に守られる」 実際は強く効きますが、あくまで確率的です。絶対に守らせたいことは、権限設定やコードで塞ぎます（Domain 2・Domain 5）。

ポイント役割の使い分けを誤ると、指示が薄まる。恒久ルールは system、可変の入力は user。
