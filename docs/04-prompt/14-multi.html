4-14　多重レビュー

1回の判定を信じない構成

見落としが致命的な場面では、同じ入力を複数回・複数の観点で通します。

BLUEPRINT 4.6Design multi-instance and multi-pass review architectures

ゴール多重化の是非をコストで判断できる。

ポイント横に並べる＝観点を変える。縦に重ねる＝役割を変える。どちらも「1回の判定を信じない」ための構成。

組み合わせる 1回目で候補を広く挙げ（再現率を優先）、2回目で1件ずつ「本当に該当するか」を検証する（適合率を優先）。
2回目は1件が1リクエストになるので、件数が多いならバッチ処理と相性が良いです（Task 4.5）。

倍のコストを払う価値があるか

多重レビューは回数ぶん確実に高くなります。使いどころを絞る必要があります。

多重にする価値があるやりすぎ
どんな場面か 見落とすと取り返しがつかない（安全性・法務・課金）／件数が少なく、1件の重みが大きい／人が全部見るには多すぎる 1回で十分な単純な分類にまで重ねる／同じ指示をただ3回繰り返す／検証で落ちても結局そのまま採用する
共通しているのは 見落としのコストが、追加の実行コストより大きい 同じ見落としが3回起きるだけ

ポイント多重化の判断は「精度が上がるか」ではなく「見落としのコストが実行コストを上回るか」。

なぜ「もう1体」でなければならないのか 同じセッションで書かせたものを同じセッションで見直させると、書いたときの考えがそのまま残っています。 「なぜそう書いたか」を覚えている状態なので、自分の判断を疑う側に回りにくい ── 見直しても「これでよい」に着地します。
別のインスタンスは、その考えを持っていません（文脈が切れていること ─ session context isolation）。コードだけを見て判断するので、書いた側が当然と思っていた前提にも引っかかります。 「もっとよく見直して」と頼むことや、考える時間を延ばすことでは代わりになりません ── 足りないのは能力ではなく、独立していることだからです。
安く重ねる工夫 ・2回目以降は対象を絞る（1回目で候補になったものだけ検証する）── これが最も効く。全件を2回通す必要はない
・急がない検証はバッチに回す（半額）
・共通の長いプロンプトは前に置いてキャッシュを効かせる（前提編）
誤解「多重にすれば精度が上がる」 実際は上がるのは観点や役割を変えたときだけ。同じ指示の繰り返しは、コストだけが倍になります。
