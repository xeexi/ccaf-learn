4-8　few-shot ─ 例を見せる

説明を増やすより、例を1つ見せる

出力の形や粒度は、言葉で説明するより実物を見せたほうが速く伝わります。

BLUEPRINT 4.2Apply few-shot prompting to improve output consistency and quality

ゴール例をどこから選ぶべきか答えられる。

✗ 説明を厚くする ─ 条件を言葉で積み上げる

簡潔に、箇条書きで、専門用語は避けて、
1項目は40字以内で、語尾は統一して…

→ 条件が増えるほど、どれかが抜ける。
  しかも、どれが抜けたかは出力を見るまで分からない

○ 例を1つ見せる ─ 入力と出力を対で

入力: この関数は何をする？
出力: 役割　: 注文を金額順に並べ替える
      引数　: orders（配列）
      戻り値: 並べ替え済みの配列

→ 上のような条件は、ひとつも書いていない

ポイント曖昧な依頼を長文で補うより、実物を1つ。ただし入力と出力を対で示す。

その1つが、同時に伝えているもの 形式（項目の並び・記号・長さ）／粒度（どこまで細かく書くか）／語調（です・ます／体言止め）
これらを言葉で全部書き出そうとすると、条件が増えて、どれかが抜けるという先の問題に戻ります。出力だけ見せても「どんなときにその形にするのか」が伝わらないので、入力とセットにします。
例は「見た形をなぞらせる」ためではない 2〜4件でよいのは、例に無い場面へも当てはめてくれるからです。 「この入力ではこう判断した、なぜならこうだから」と選んだ理由まで書いた例を見せると、 初めて見る形の入力にも同じ考え方が適用されます。
逆に、理由を書かずに正解だけ並べるとその形にだけ反応するようになります ── 例と少し違う入力で崩れるのは、たいていこれです。
誤解「例は多いほどよい」 実際は例もコンテキストを消費します。効くのは最初の1〜3個で、そこから先は伸びが鈍ります。数より、下で扱う選び方です。

例は「難しいところ」から選ぶ

いちばん典型的な例を並べても、判断に迷う場面では効きません。

ゴール効く例と、効かない例を見分けられる。

選ぶ例中身効くか
典型例ばかり 誰が見ても明らかな例を3つ 効かない　もともと迷わない場面にしか当たらない。例を足したのに精度が上がらないときは、たいていこれ
境界の例 「これは該当する／しない」のきわどい例 効く　言葉で線を引くより速く伝わる
誤りの例 「こう答えたのは誤り。理由は…」を対で示す 効く　避けるべき方向が伝わる

ポイント例の価値は数ではなくどこを示すか。境界と誤りを見せると、判断が安定する。

例を作るときの3つの決まりごと ① 形式を完全に揃える（例どうしがずれていると、そのずれごと学ぶ）
② 出現しうる分類を偏りなく含める（片寄ると、その分類に引っぱられる）
③ 実際に間違えた出力を、次の例として足していく
とくに③が、いちばん効率のよい増やし方です。探す手間がなく、必ず境界の例になっているから。
Domain 3 とのつながり ③は、Domain 3 の「反復的な改善」と同じ考え方です。気づいた基準を会話で終わらせず、例として書き戻す。次回から自動で効きます。
