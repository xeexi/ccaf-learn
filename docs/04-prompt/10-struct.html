4-10　構造化出力と tool_choice

JSONは「お願い」ではなく「型」で受け取る

ゴール出力の形を保証する手段を選べる。

アプリ→Claude→アプリ

文章で「JSONで返して」と頼むと、前置きや揺れが混ざります。スキーマ（ツール定義）で受け取れば、形が保証されます。

BLUEPRINT 4.3Enforce structured output using tool use and JSON schemas

✗ 文章でお願いする

［指示］ JSON形式で出力してください

［返ってきたもの］
はい、こちらが結果です:
```json
{ "name": "田中", "amount": "1,200円" }

→ 前置き・囲み・型の揺れが混ざる。金額を数値として扱えない

○ スキーマ（ツール定義）で受け取る

［定義］
"input_schema": { "name": "string", "amount": "integer" }
"required": ["name", "amount"]

［返ってきたもの］
{ "name": "田中", "amount": 1200 }

→ 型と必須項目が守られる。囲みも前置きもない

ポイント構造化データ抽出は、プロンプトを工夫する問題ではなく、スキーマを設計する問題。値が無い場合の表現（null を許すか）まで決めておく。

ここでいうスキーマは、ツール定義の input_schema そのもの 抽出したい形をツールの引数として定義し、そのツールを呼ばせることで、受け皿を先に用意します（Domain 2〈ツール定義は3つの部品〉）。 記入欄の形を先に決めておくということです。
決めておくべきこと ・型（金額は文字列か整数か）
・必須かどうか（required）
・値が見つからなかったときどう書くか（null を許すのか、空文字か、そもそも項目を出さないのか）
最後のひとつを決め忘れると、実運用でいちばん揉めます。
誤解「うまく指示すればきれいな JSON が返る」 実際は返ることも多いですが、保証されません。前置き、コードブロックの囲み、全角記号。構造化抽出はプロンプトの問題ではなくスキーマ設計の問題です。

ツールを「使わせる」4つの指定

ゴールtool_choice の4つを使いどころで選び分けられる。

tool_choice は、道具を使うかどうかの判断をこちらが決めるためのものです。

tool_choice何が起きるか使いどころ
auto（既定）使うかどうかをモデルが決める ふつうの道具はこれ
anyどれかは必ず使う。どれを使うかはモデルが選ぶ 道具は複数あるが、文章で答えられては困るとき
toolこの道具を必ず使う（名前で指定） 構造化出力を強制したいときはこれ
none道具を使わせない 道具は渡したまま、今回だけ文章で答えさせたいとき

これで、必ず extract_invoice の形で返ってくる ＝ 構造化出力の強制

"tool_choice": { "type": "tool", "name": "extract_invoice" }

ポイント「JSONで返して」と頼むのではなく、ツールを使わざるを得なくする。これが構造化出力の強制。

誤解「any や tool でも、先に説明させてから使わせられる」 実際は前置きの文章は出なくなります。「説明してから使って」と書いても効きません。説明も欲しいなら auto ＋ 指示文にします。
設問での問われ方 「請求書から項目を抽出したい。必ずJSONで受け取りたい」→ tool_choice を tool にして抽出用ツールを指定。
「道具は渡しておくが、今回は使わせたくない」→ none。ツール定義を外す必要はありません。

※ どの型にも "disable_parallel_tool_use": true を添えられます。付けると1回の応答で呼ばれる道具が1つに制限されます（Domain 1〈子はどう起こすのか〉の並列ツール使用を切る指定）。抽出のように「1件につき1つ」と決まっている場面で使います。

受け皿の形で、揺れを潰す

ゴール値がないときに作らせない書き方を言える。

スキーマは「形を決める」だけでなく、迷ったときの逃げ道まで決めるものです。

正常系の形と、異常系の逃げ道を両方決める

"properties": {
  "amount":   { "type": "integer" },1
  "currency": { "enum": ["JPY", "USD"] },2
  "due_date": { "type": ["string", "null"] },3
  "category": { "enum": ["物品", "役務", "その他"] },4
  "detail":   { "type": "string" }
},
"required": ["amount", "currency", "category"]5
  1. 1型を絞る。integer にすれば "1,200円" のような文字列は入りません。
  2. 2enum で選択肢を閉じる。自由記述にすると「円 / JPY / 日本円」のように表記が割れます。
  3. 3null を許す。読み取れなかった項目を「無い」と表せないと、それらしい値を作られます。
  4. 4「その他」＋ detail。用意した分類に収まらない入力の逃げ道です。これが無いと、近い分類へ無理に押し込まれます。
  5. 5required で必ず埋まるべき項目を宣言します。逆に言えば、埋まらないことがある項目は入れません。
スキーマで縛れないばらつきは、指示側で吸収する enum や型で縛れるのは選択肢が決まっているものだけです。「2026年1月1日」「2026/01/01」「R8.1.1」のように 元の書類ごとに書き方が違うものは、スキーマでは1つに寄せられません。
そういう項目はプロンプト側に「どう直すか」を書きます ── 「日付は YYYY-MM-DD に直す」「金額は数値だけにして、通貨は別項目へ」。 厳しいスキーマと、そろえ方の指示はセットです。
さらに厳密にしたいとき ツール定義に strict: true を付けると、入力がスキーマに厳密に従うことを保証できます。
tool_choice: any と組み合わせると、「どれかのツールが必ず呼ばれ、かつ入力がスキーマどおり」という状態を作れます。

ポイントスキーマ設計とは、正常系の形と異常系の逃げ道を両方決めること。後者を忘れると運用で破綻する。
