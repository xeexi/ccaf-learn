4-10　構造化出力と tool_choice

JSONは「お願い」ではなく「型」で受け取る

文章で「JSONで返して」と頼むと、前置きや揺れが混ざります。スキーマ（ツール定義）で受け取れば、形が保証されます。

BLUEPRINT 4.3ツール利用と JSON スキーマによる構造化出力の強制

ゴール出力の形を保証する手段を選べる。

図の読み方

  1. 1左（赤）が文章でお願いした場合。上が指示、下が返ってきたものです。
  2. 2返ってきたほうをよく見てください。前置きの一文、コードブロックの囲み、そして "1,200円" という文字列が混ざっています。数値として扱えません。
  3. 3右（緑）がスキーマで受け取った場合。上が定義、下が結果です。
  4. 4こちらは型と必須項目が守られ、金額が整数で返っています。囲みも前置きもありません。

スキーマで受け取るというのは、記入欄の形を先に決めておくということです。書き方が割れる余地をなくします。ここでいうスキーマは、ツール定義の input_schema そのものです（Domain 2「ツール定義の解剖」）。抽出したい形をツールの引数として定義し、そのツールを呼ばせることで、受け皿を先に用意します。

決めておくべきこと ・型（金額は文字列か整数か）
・必須かどうか（required）
・値が見つからなかったときどう書くか（null を許すのか、空文字か、そもそも項目を出さないのか）
最後のひとつを決め忘れると、実運用でいちばん揉めます。
誤解「うまく指示すればきれいな JSON が返る」 実際は返ることも多いですが、保証されません。前置き、コードブロックの囲み、全角記号。構造化抽出はプロンプトの問題ではなくスキーマ設計の問題です。

ポイント構造化データ抽出は、プロンプトを工夫する問題ではなく、スキーマを設計する問題。値が無い場合の表現（null を許すか）まで決めておく。

ツールを「使わせる」4つの指定

tool_choice は、道具を使うかどうかの判断をこちらが決めるためのものです。

図の読み方

  1. 1auto ─ 既定値。使うかどうかをモデルが判断します。ふつうの道具はこれ。
  2. 2any ─ どれかは必ず使う。ただしどれを使うかはモデルが選びます。
  3. 3tool ─ この道具を必ず使う。名前で指定します。構造化出力を強制したいときはこれです。
  4. 4none ─ 道具を使わせません。道具を渡したまま、今回だけ文章で答えさせたいときに使います。
  5. 5下の注意が実務で効きます。any や tool を指定すると、前置きの文章が出なくなります。「先に説明してから」と書いても効きません。
設問での問われ方 「請求書から項目を抽出したい。必ずJSONで受け取りたい」→ tool_choice を tool にして抽出用ツールを指定。
「道具は渡しておくが、今回は使わせたくない」→ none。ツール定義を外す必要はありません。

ポイント「JSONで返して」と頼むのではなく、ツールを使わざるを得なくする。これが構造化出力の強制。

受け皿の形で、揺れを潰す

スキーマは「形を決める」だけでなく、迷ったときの逃げ道まで決めるものです。

図の読み方

  1. 1型を絞る。金額を integer にすれば、"1,200円" のような文字列は入りません。
  2. 2enum で選択肢を閉じる。自由記述にすると「円 / JPY / 日本円」のように表記が割れます。
  3. 3null を許す。読み取れなかった項目を「無い」と表せないと、それらしい値を作られます。
  4. 4「その他」＋ detail。用意した分類に収まらない入力の逃げ道です。これが無いと、近い分類へ無理に押し込まれます。
  5. 5required で必ず埋まるべき項目を宣言します。逆に言えば、埋まらないことがある項目は required に入れません。
さらに厳密にしたいとき ツール定義に strict: true を付けると、入力がスキーマに厳密に従うことを保証できます。
tool_choice: any と組み合わせると、「どれかのツールが必ず呼ばれ、かつ入力がスキーマどおり」という状態を作れます。

ポイントスキーマ設計とは、正常系の形と異常系の逃げ道を両方決めること。後者を忘れると運用で破綻する。
