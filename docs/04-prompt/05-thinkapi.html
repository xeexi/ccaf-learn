4-5　thinking の実物 ─ 何を送り、何が届くか

前の節は「どこで考えさせるか」の判断でした。ここは API 側の仕様です。何を1つ足すと有効になり、応答と途中経過がどう変わるかを見ます。

ゴールthinking でリクエストと応答がどう変わるか言える。

実物を見る ─ 拡張思考のリクエストと応答

前の節の②（API の thinking）を、実際の JSON で確認します。

リクエスト

{
  "thinking": { "type": "enabled", "budget_tokens": 10000 },1
  "max_tokens": 16000,2
  "messages": [ … ]
}

応答

"content": [
  { "type": "thinking", "thinking": "…条件を並べて順に確かめる…" },3
  { "type": "text", "text": "結論は…" }
]
  1. 1付けるのはこれだけ。「どう考えるか」を書く必要はありません。予算の最小は1024トークン。
  2. 2思考は出力の一部なので、budget_tokens は max_tokens より小さくします。
  3. 3content に thinking ブロックが増えます。中身は要約された思考で、内部の全文が出るわけではありません。
  4. 4この thinking ブロックの分も出力トークンとして課金されます。

ポイント付けるのは thinking フィールドだけ。応答に thinking ブロックが増え、そのぶん出力トークンを食う。

thinking の最中、アプリには何が届いているのか

ストリーミングを使うかどうかで、答えが正反対になります。

図の読み方

  1. 1①が stream なし。リクエストを送ったあと、モデルが思考を書いている間、アプリには何も届きません。完成してから content も stop_reason もまとめて1回で返ります。
  2. 2②が stream: true。思考は thinking_delta として少しずつ届きます。アプリの画面で「考えています…」の中身が流れて見えるのは、これです。ご想像のとおり、送られています。
  3. 3ただし流れるのは一方向だけです。アプリが途中で何かを返すことはありません。往復は1回のままで、変わっているのは「届き方」だけ。1回の応答を細切れに受け取っているだけなので、呼び出し回数もトークン数も変わりません。
  4. 4順番は決まっています。message_start →（ブロックごとに）content_block_start → delta の繰り返し → content_block_stop → 最後に message_delta → message_stop。
  5. 5いちばん大事なのがstop_reason がどこで来るか。最後の message_delta です。つまりストリーミングでも、アプリが分岐できるのは最後。途中の delta を見て「もう答えが出た」と判断することはできません（Domain 1「stop_reason で分岐」）。

ポイントthinking 中に届くのは、stream: true のときだけ。しかも一方向で、往復は増えない。stop_reason が来るのは最後の message_delta。

※ thinking ブロックの最後には signature_delta（署名）が届き、その直後に content_block_stop になります。この署名は、上で触れた「thinking ブロックをそのまま履歴に戻す」ときの検証に使われるものです。
