4-5　実物を見る ─ thinking の JSON

ゴールthinking を有効にすると何がどう変わるか、実物で指せる。

アプリ→Claude→アプリ

考える過程をモデルに出させる指定を、実際の JSON で見ます。送る側に足すのは1行だけですが、変わるものは2つあります ── 応答の形と、トークンの使われ方です。

① 応答の形 ─ 答えの前に、思考のブロックが入る

ゴール有効にする前と後で、応答のどこが違うか指せる。

〈考えさせる ─ thinking〉の②（API の thinking）を、送る側と返る側の両方で確認します。

リクエスト

{
  "thinking": { "type": "enabled", "budget_tokens": 10000 },1
  "max_tokens": 16000,
  "messages": [ … ]
}

応答 ─ thinking なし

"content": [
  { "type": "text", "text": "結論は…" }
]

応答 ─ thinking あり

"content": [
  { "type": "thinking", "thinking": "…条件を並べて順に確かめる…" },2
  { "type": "text", "text": "結論は…" }
]
  1. 1足すのはこの1行だけ。「どう考えるか」は書きません。budget_tokens は最小1024。
  2. 2返る側は必ずこのブロックから始まります。答えの text はその後ろなので、content の先頭を答えとして読んでいたアプリは有効にした日に壊れます。中身は要約された思考で、内部の全文ではありません。

ポイント送る側に足すのは thinking フィールド1つ。返る側は thinking ブロックで始まり、答えの text はその後ろに来る。

② トークンの使われ方 ─ 思考と答えが同じ枠を分け合う

ゴール考える分が増えると答えに残る分が減ることを、数で言える。

思考は「おまけ」ではなく出力そのものです。だから max_tokens の枠を、答えと分け合います。

ポイント思考も出力トークンとして課金される。max_tokens は思考と答えの合計の上限なので、考えさせるほど答えに残る枠は減る。

※ ストリーミング（stream: true）は試験の範囲外です ── 公式 Exam Guide が「Streaming API implementation or server-sent events」を出題対象外と明記しています。 生成しながら少しずつ届く形にできますが、届き方が変わるだけで、往復の回数もトークン数も変わりません。
押さえるのは1点だけ ── 途中で届くものを見て「もう答えが出た」と判断することはできません。アプリが分岐できるのは stop_reason が来てからです（Domain 1〈stop_reason で分岐する〉）。
