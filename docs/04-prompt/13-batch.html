4-13　バッチ処理

急がない大量処理は、まとめて投げる

1件ずつ同期で投げる代わりに、Message Batches API でまとめて非同期に処理します。料金が半分になります。

BLUEPRINT 4.5Design efficient batch processing strategies

ゴールバッチに回す判断基準と、順序への対処を言える。

ポイント判断基準はひとつ ── すぐ答えが要るか。要らないなら、半額で通せる。

向く仕事 大量の評価セットの実行 ／ 投稿の一括分類・モデレーション ／ 蓄積した文書からの一括抽出 ／ 過去データの棚卸し
いずれも「今すぐ答えが要らない」点が共通です。

順序は保証されない ─ custom_id で対応づける

結果は投げた順に返ってきません。1件ごとに付けた ID で突き合わせます。

送るとき ─ 1件ごとに custom_id を付ける

{ "custom_id": "inv-001", "params": {…} }
{ "custom_id": "inv-002", "params": {…} }
{ "custom_id": "inv-003", "params": {…} }
英数字・ハイフン・下線／64文字まで

返ってくるとき ─ 順番はばらばら

{ "custom_id": "inv-003", … }
{ "custom_id": "inv-001", … }
{ "custom_id": "inv-002", … }
配列の位置で対応づけてはいけない

ポイント順序は保証されない ── これがバッチ処理で最初に踏む落とし穴。ID で対応づけるのが唯一の正解。

1件ごとの結果意味課金
succeeded成功あり
erroredエラー。「直して投げ直す」ものと「そのまま再試行してよい」ものに分かれるなし
canceled取り消しなし
expired24時間で処理しきれなかったなし
締め切りから、投げる間隔を逆算する バッチは最大24時間かかります。「受け取ってから30時間以内に返す」約束なら、溜めてよいのは6時間まで ── それを超えると、処理が始まる前に締め切りが来ます。
実際には余裕を見て4時間ごとに投げるように組みます。「1日1回まとめて」は、締め切りのある仕事では成り立ちません。
全件を流す前に、少量で試す 2,000件を投げて、返ってきたものの半分が使えなかったら、やり直しは丸ごと1日後です（結果は最大24時間かかる）。
先に20〜50件で流し、通らなかったものを見てからプロンプトを直します。 1回目で通る率を上げておくほうが、結局いちばん速く終わります ── バッチはやり直しが高くつくのが唯一の弱点です。
できること／できないこと 使える：ツール定義・複数ターンの会話・拡張思考・画像。「バッチだから単発の質問しか投げられない」わけではありません
使えない①：stream: true（結果はまとめて返るため）
使えない②：1リクエストの中でツールを実行して結果を返すこと。tool_use が返っても、 その場で実行して続きを進める往復がありません ── つまりバッチの中でエージェントループは回せません。 ツールを使う仕事をバッチに乗せるなら、1往復で終わる形に切ります。
※ 処理に時間がかかるため、共通の長いプロンプトを使うならキャッシュは長め（1時間）の設定と相性が良くなります。
