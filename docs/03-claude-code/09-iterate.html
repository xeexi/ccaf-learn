3-9　反復的な改善

ゴール回し方の型を4つ挙げ、改善をどこへ書き戻すか答えられる。

出力が確率的である以上、一発勝負は分が悪い。小さく回して、そのつど基準を書き足していきます。

BLUEPRINT 3.5Apply iterative refinement techniques for progressive improvement

設問での問われ方 「生成されるコードが毎回チームの規約から外れる。どうするか」
→ その場で指摘し直すのではなく、規約を CLAUDE.md に書いて次回以降に効かせる。
「大きな機能を一度に作らせたらうまくいかない」→ plan mode で方針を合意 → 小さい単位に分けて実行 → 都度確認。

ポイント改善を会話の中で終わらせない。設定ファイルに書き戻して初めて、次回から効く。

回し方の型は4つ

ゴール4つの型を、効く場面で選び分けられる。

「小さく回す」の中身です。言葉を足すのではなく、渡すものを変えるのが型になっています。

型やること効く場面
入出力の例を見せる 「この入力なら、この出力」を2〜3件添える 言葉で書くと解釈がぶれるとき（整形・変換・分類）。散文で条件を足すより速い
先にテストを書く 期待する挙動・境界・性能をテストにしてから実装させ、落ちたテストを渡してもう一度 正しさの基準が決められるとき。直し方を言わずに基準だけ渡せる
先に質問させる 実装の前に「気になる点を先に質問して」と頼む 自分が不慣れな領域。考慮漏れが、作り終わる前に出てくる
まとめて1通か、順番か 絡み合う指摘は1通にまとめて、独立した指摘は1つずつ順番に 直したいところが複数あるとき

ポイント回すときに増やすのは言葉ではなく材料 ── 例・テスト・質問。相互に絡む指摘だけは1通にまとめる。

なぜ「まとめて1通」と「順番に」を分けるのか 絡み合う指摘を順番に直させると、前の修正を壊しながら進みます。「A を直して」→ 直る →「B も直して」→ A が戻る、という往復になります。
逆に独立した指摘を1通にまとめると、どれかが抜けます（前提編・Domain 4 の「条件が増えるとどれかが抜ける」）。
判断は「この2つは同じ箇所に触るか」だけです。
誤解「うまくいかないときは、指示をもっと詳しく書けばよい」 実際は散文を足すほど、どれかが抜けます。詳しく書くより、実物を渡す ── 例・落ちたテスト・質問への答え。どれも「読み違えようがない材料」です。
