3-12　settings.json と permissions

設定ファイルはどこが優先されるか

同じ項目が複数の場所にあるとき、上にあるものが勝ちます。

BLUEPRINT 3.6CI/CD への統合

ゴールCLAUDE.md と settings.json を「足し算／勝ち負け」で言い分けられる。

図の読み方

  1. 1一番上が組織の管理設定。利用者側で上書きできません。CLAUDE.md の管理ポリシーと同じ考え方です。
  2. 2次が起動時のCLIフラグ。その場限りの指定が、ファイルより強く効きます。
  3. 3settings.local.json は自分専用。共有しない設定はここ。settings.json はチーム共有で git に入れます。
  4. 4一番弱いのがホームディレクトリの設定。自分の全プロジェクトに効く既定値です。ここで注意 ── 「個人に近いほど弱い」わけではありません。settings.local.json（自分だけ）は settings.json（チーム共有）より強いです。
CLAUDE.md との違い CLAUDE.md は連結（全部が足し合わされる）。settings.json は優先順位で決着（強いほうが勝つ）。
同じ「階層がある」でも扱いが違うので、設問で入れ替えられると間違えます。

ポイントCLAUDE.md＝足し算、settings.json＝勝ち負け。ここを混同しない。

allow / deny で通れる道を決める

ツール名とパターンの組で、許可と禁止を書きます。

図の読み方

  1. 1書式は ツール名(パターン)。Bash(npm test *) のように、コマンドの形まで絞れます。
  2. 2* でワイルドカード。Bash(npm run *) なら npm run で始まるものだけ通ります。
  3. 3allow は「確認なしで通す」。毎回聞かれると邪魔になる、やり直せる操作を並べます。
  4. 4deny は「通さない」。.env の読み取りや rm -rf のように、事故が致命的なものを塞ぎます。
  5. 5どちらにも該当しないものはその場で確認されます。だから deny を書くことに意味があります。
設問での問われ方 「秘密情報のファイルを絶対に読ませたくない」→ deny に Read(./.env)。CLAUDE.md に「読まないで」と書くのは弱い対策。
「テストは毎回自動で走らせたいが、いちいち確認されて煩わしい」→ allow に Bash(npm test *)。

ポイントプロンプトでのお願いは確率的、permissions は決定的。取り返しのつかない操作は必ず後者で塞ぐ。
