3-12　settings.json と permissions

設定ファイルはどこが優先されるか

ゴールCLAUDE.md と settings.json を「足し算／勝ち負け」で言い分けられる。

どの操作を許すか・禁じるかは、設定ファイルで決めます。同じ項目が複数の場所にあるときは、優先順位の上にあるものが勝ちます。

BLUEPRINT 3.6Integrate Claude Code into CI/CD pipelines

強さ置き場所誰の設定か
1（最強）組織の管理設定（Managed settings） 利用者側で上書きできない。CLAUDE.md の管理ポリシーと同じ考え方
2起動時の CLI フラグ（--model など） その場限りの指定が、ファイルより強く効く
3.claude/settings.local.json 自分だけ・共有しない
4.claude/settings.json プロジェクト・git で共有
5（最弱）~/.claude/settings.json 自分の全プロジェクトに効く既定値

ポイントCLAUDE.md＝足し算（全部が連結される）、settings.json＝勝ち負け（強いほうが勝つ）。同じ「階層がある」でも扱いが違うので、設問で入れ替えられると間違える。

誤解「個人に近いほど弱い」 実際はsettings.local.json（自分だけ）は settings.json（チーム共有）より強いです。弱いのはホームディレクトリのほう ── 「個人／チーム」ではなく「その場に近いか」で並んでいます。

allow / deny で通れる道を決める

ゴール許可と禁止に何を並べるか言える。

ツール名とパターンの組で、許可と禁止を書きます。

.claude/settings.json　─　書式は ツール名(パターン)

{ "permissions": {
    "allow": [ "Bash(npm test *)", "Read(~/.zshrc)" ],
    "deny":  [ "Bash(rm -rf *)", "Read(./.env)" ]
} }
並べる場所起きること何を並べるか
allow確認なしで通す やり直せる操作。毎回聞かれると邪魔になるもの（テスト実行、読み取り）
denyそもそも通さない やり直せない操作と見せたくないファイル（rm -rf、.env の読み取り）
どちらにも無いその場で確認される 既定の挙動。だから deny を書くことに意味がある

ポイントプロンプトでのお願いは確率的、permissions は決定的。取り返しのつかない操作は必ず後者で塞ぐ。

設問での問われ方 「秘密情報のファイルを絶対に読ませたくない」→ deny に Read(./.env)。CLAUDE.md に「読まないで」と書くのは弱い対策。
「テストは毎回自動で走らせたいが、いちいち確認されて煩わしい」→ allow に Bash(npm test *)。
* はワイルドカード。Bash(npm run *) なら npm run で始まるものだけ通ります。
