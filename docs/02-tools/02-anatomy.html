2-2　ツール定義は3つの部品でできている

ゴール3つの部品が何を決めているか言える。

モデルは、どの道具を使うかを何を見て決めているのか。渡している定義は name（呼び名）・description（いつ使うか）・input_schema（何を渡すか）の3つでできていて、判断に効くのは description だけです。

BLUEPRINT 2.1Design effective tool interfaces with clear descriptions and boundaries

ポイントdescription に書くべきは「何をするか」より「どんなときに使うか」。判断の条件を言語化する。

書き直しの型 ✗ 何をするかだけ："コーディング規約を取得する"
○ 何をするか＋いつ呼ぶか＋いつ呼ばないか：
"コーディング規約を取得する。命名やフォーマットに触れる前に必ず呼ぶ。一般的な設計方針の質問には使わない"
3つ目の「いつ呼ばないか」が境界です。これがないと、近い話題のたびに呼ばれます。
説明文を直しても呼ばれないときは、system を疑う system に「調べものはまず検索から」と書いてあると、モデルはその語に引きずられて、丁寧に書いた description より名前が「検索」に近い道具を選びます。 ツールの選ばれ方は、道具の説明文だけで決まっていません。system の言葉と、道具の名前や説明文が勝手に結びつくことがあります。
呼ばれ方がおかしいときは、system に特定の道具を連想させる語が入っていないかを見ます。
誤解「description はコードのコメントのようなもの。人間が読む用」 実際はプロンプトの一部です。しかも常にコンテキストを消費しています（前提編）。丁寧に、しかし冗長にならないよう書きます。
