2-5　MCP という差込口

MCP＝ツールをつなぐ共通の差込口

アプリごとに個別実装していた接続を、共通の規格にまとめたものです。作る量が「掛け算」から「足し算」になります。

BLUEPRINT 2.4MCP サーバの統合

ゴールMCP が何を解決する仕組みか説明できる。

図の読み方

  1. 1「MCPなし：N × M 本」（左）── アプリ3つ×サービス3つで線が9本。すべて個別に実装したものです。
  2. 2「MCPあり：N ＋ M 本」（右）── 中央の規格を経由するので3＋3 の6本。効き目が出るのは増やすときです。アプリを1つ足すと、左では3本増え、右では1本しか増えません。
  3. 3下の帯が3層の呼び名。設問はこの語彙で書かれるので、どれがどれかだけ押さえます ── 動かす側がホスト、つながれる側がサーバです。

3層の関係と、よくある誤解

たとえるなら

USBです。規格が決まる前は機器ごとに専用ケーブルが必要でしたが、差込口の形を決めたことで、作る量が掛け算から足し算になりました。賢さが変わるのではなく、つなぐ手間が変わります。

3層の関係 ホスト（Claude Code など、実際に動かすアプリ）
─ クライアント（つなぐ側の口）
─ サーバ（Slack、GitHub、DB など、つながれる側）
サーバが提供できるのは tools だけではありません。resources（読める資料）や prompts（定型の手順）も渡せます。
誤解「MCP を使うとモデルが賢くなる／速くなる」 実際は賢さは変わりません。変わるのはつなぐ手間だけです。「新しいサービスと連携したい」という要件で、自前実装より既存の MCP サーバを選ぶのはそのためです。

ポイント「新しいサービスを繋ぎたい」という要件では、独自実装より既存の MCP サーバを使うのが素直な答えになる。

実物を見る ─ .mcp.json でサーバを登録する

MCPサーバをどこに書くかで、誰に見えるかが変わります。チームで共有したいならプロジェクト直下の .mcp.json です。

プロジェクト直下の .mcp.json

{
  "mcpServers": {1
    "shared-server": {
      "type": "http",2
      "url": "https://example.com/mcp" },
    "db-tools": {
      "command": "npx",3
      "args": ["-y", "@example/db-server"],
      "env": { "DB_URL": "${DB_URL}" } }4
  }
}
  1. 1mcpServers の下に、サーバ名をキーにして並べます。
  2. 2リモートに繋ぐなら type と url。
  3. 3手元でプロセスを起動するなら command と args。
  4. 4${DB_URL} のように環境変数を展開できます。鍵そのものを書かずに済むので、このファイルをリポジトリに入れられるのがポイントです。

3つのスコープ ─ 誰に見えるか

同名で重複したら local > project > user の順で勝つ local（既定）　自分だけ・そのプロジェクトだけ　→ ~/.claude.json
project　チーム全員　→ .mcp.json（バージョン管理に入れる）
user　自分だけ・全プロジェクト　→ ~/.claude.json
誤解「.mcp.json に書けば、黙ってすぐ使われる」 実際は対話セッションでは初回に承認を求められます。他人のリポジトリを開いた瞬間に勝手に繋がらないための仕組みです。

ポイント「チーム全員が同じツールを使えるようにしたい」の答えが .mcp.json（project スコープ）。個人の実験は local。設定ファイルの置き場所＝共有範囲という読み方は、Domain 3 の CLAUDE.md や settings.json とまったく同じです。
