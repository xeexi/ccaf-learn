2-4　失敗は読める形で返す

ツールの失敗は「読める文章」で返す

例外で止めるとループが死にます。何が起きたかを言葉で返せば、Claudeは自分で直して再試行できます。

BLUEPRINT 2.2MCP ツールの構造化エラー応答

ゴール失敗をどう返すと再試行につながるか説明できる。

図の読み方

  1. 1左（赤）が落とす・黙る場合。例外を投げる、「エラー」とだけ返す、空文字を返す。
  2. 2その下がどうなるか。どちらに転んでも、モデルは同じ引数でもう一度呼びます。何が悪かったかを渡していないので、直しようがないからです。
  3. 3右（緑）が読める形で返す場合。何が起きたかを、そのまま文章で tool_result に入れます。
  4. 4その下では、引数を直して呼び直せています。つまり返す文の質が、そのまま再試行の質になります。「エラーが発生しました」では、何も直せません。
返す文に入れる2つ ① 何が起きたか：「pattern '[' は正規表現として解釈できません」
② どう直せるか：「文字として探すなら '\[' のようにエスケープしてください」
①だけだと、同じ間違いを繰り返すことがあります。
誤解「親切にエラーを返せば、あとは勝手に直してくれる」 実際は直せないまま無限に再試行することがあります。再試行の上限は外側で持つ（Domain 1の反復上限）ことをセットで用意します。

ポイント返す文には「何が起きたか」と「どう直せるか」を両方入れる。ただし無限に再試行させないよう、回数の上限は外側で持つ。

実物を見る ─ 失敗を返す tool_result

上の考え方を、実際にアプリが送る JSON で確認します。

ツールが失敗したときに、アプリが送るもの

{ "role": "user", "content": [1
  { "type": "tool_result",
    "tool_use_id": "toolu_01A...",2
    "content": "pattern '[' は正規表現として解釈できません。文字として探すならエスケープしてください",3
    "is_error": true4 } ] }
  1. 1失敗でも成功でも、送る形は同じです。role: "user" のメッセージとして返します。例外を投げてループを止めるのではなく、こう返す、という話でした。
  2. 2どの要求に対する結果かの対応づけ。tool_use の id をそのまま入れます。ずれると会話が壊れます。
  3. 3ここが本体。Claudeが読むのはこの文章です。「何が起きたか」＋「どう直せるか」を書きます。
  4. 4is_error: true は「これは失敗だ」という印。付けてもループは止まりません。止めるためのフラグではない、というのが試験で狙われるところです。

ポイントis_error は処理を止めるためのものではない。Claudeは content の文章を読んで次を決めるので、直し方をそこに書く。止めるのは外側の反復上限。

※ 同じ user メッセージに文章も添えたい場合は、tool_result を先に置きます。文章を先に書くと 400 エラーになります。content は文字列でも、ブロックの配列でもかまいません。
