まず、全体の流れ

あなたの入力は「アプリ → API → モデル」と流れます。モデルは必要なら道具（ツール）を使い、結果を受け取ってから答えます。

図の読み方

  1. 1アプリ（Claude Code や自作プログラム）が、この図で実際に動いている唯一の主体。以降のすべてを呼び出します。
  2. 2API はその窓口。messages という形にまとめて送ります。
  3. 3Claude（モデル本体）は、読んで次に何を書くかを決めるだけ。
  4. 4ツールを実際に叩くのはアプリ。モデルは「使いたい」と言っただけです。下の点線が、その結果をふまえた答えが返る経路。

ポイントモデル本体（LLMとしてのClaude）はネットにも DB にもアクセスしない。「この道具を使いたい」と言うだけで、実際に動かすのは外側のプログラム。この分業が、あとの全ての話の土台になる。

用語について：この教材で単に「Claude」と書いたときは、図の右から2つ目にあたるモデル本体（LLM）を指します。アプリである Claude Code や Claude デスクトップアプリは、その外側の「アプリ」の位置にあります（Domain 3）。

同じ図を、実際のやり取りに置き換える

上の図を、「注文A-12はどうなってる？」という1回の質問で追いかけます。箱の名前は図と同じです。

どの箱が、何をするか

  1. 1あなたがアプリに「注文A-12はどうなってる？」と入力する。
  2. 2アプリが、その質問と使えるツールの一覧を API 経由で送る。
  3. 3Claude（モデル本体）が search_orders(order_id:"A-12") を使いたいと返す。ここでモデルの番はいったん終わる。
  4. 4アプリが実際に ツール（DB）を検索し、「配送中」を得る。検索したのはアプリで、モデルではない。
  5. 5アプリが「配送中でした」を送り直すと、Claude が「A-12 は現在配送中です」と書く。これが図の点線＝最終的な答え。

ここを取り違えると、あとが全部ずれる

誤解「Claude がファイルを消した」「Claude が検索した」 実際はClaude は消したいと言っただけで、消したのは外側のプログラム。だからこそ「消させない」も外側で決められる（Domain 2・Domain 3）。

ポイントモデル本体（LLMとしてのClaude）はネットにも DB にもアクセスしない。「この道具を使いたい」と言うだけで、実際に動かすのは外側のプログラム。この分業が、あとの全ての話の土台になる。

セクション

会話は毎回、まるごと送り直している

Claudeは前回の会話を覚えていません。「覚えているように見える」のは、毎回これまでの全メッセージを送り直しているからです。

図の読み方

  1. 1左に並ぶ箱が、送信のたびに増えていくメッセージの配列です。
  2. 21回目は1件だけ。「こんにちは」を送って、返事が返ります。
  3. 32回目は3件になっています。1回目の質問、その返事、そして新しい質問。過去のぶんも、もう一度そのまま送っています ─ ここがこのページの要点です。
  4. 4右のパネルがサーバ側の状態。前回の続きを保持しているのではなく、送られてきた配列をその場で丸ごと読んでいます。
  5. 5だから3回目・4回目と進むほど、毎回の送信量そのものが増えていきます。

ポイント「記憶」は仕組みではなく、送り直しの結果。会話履歴は資産であると同時にコストでもある。

ここから3つのことが説明できる

たとえるなら

会うたびに記憶がゼロに戻る相談相手に、これまでの経緯を書いた紙の束を毎回渡し直している状態です。会話が進むほど束は厚くなり、相手はそれを毎回最初から読み直します。

3回目に実際に送られているもの [ user:こんにちは / assistant:どうも / user:続きを ]
最初の「こんにちは」も、もう一度そのまま送られています。省略はされません。

ここから3つのことが説明できる

・会話が長くなるほど、遅く・高くなる　毎回の紙束が厚くなるので当然です。
・長い作業の途中で、最初の指示を忘れたように見える　束が厚くなり、大事な1枚が埋もれるからです（Domain 5で扱います）。
・別のセッションを開くと何も引き継がれない　紙束を渡していないので、相手にとっては初対面です。

誤解「Claude がこちらの会話を覚えていてくれる」 実際は覚えているのはアプリ側。モデルは毎回、渡された束をその場で読んでいるだけ。

ポイント「記憶」は仕組みではなく、送り直しの結果。会話履歴は資産であると同時にコストでもある。

セクション

トークンとコンテキストウィンドウ

文章は「トークン」に刻まれ、窓に入る分だけ扱える

文字ではなくトークン（単語の断片）が処理の単位です。1回のやり取りで扱える総量には上限（コンテキストウィンドウ）があります。

図の読み方

  1. 1上段が①刻む。文章がトークンという単位に分割されます（刻み方は下の注記のとおり、あくまで例です）。
  2. 2下段の太い枠がコンテキストウィンドウ。1回のやり取りで扱える総量の上限です。
  3. 3枠の中に並ぶ箱がそこに載るもの。システム指示、ツールの定義、会話履歴、そしてツールが返した結果（＝ tool_result。ここまでが送る側＝入力）。
  4. 4右下の緑が今回の出力。これからモデルが書く分で、tool_result とは別物です。入力と出力が同じ枠を共有しているのがこの図の要点です。
  5. 5右端の赤い箱が残り。どれかが太れば、他が痩せます。

ポイントウィンドウは共有資源。ツールの定義文も、ツールが返した長大なログも、同じ窓を食う。

※ 上の刻み方は説明用の例です。実際の境界はモデルのトークナイザが決めるもので、日本語の単語や文節とは一致しません。「エージ／ェント」のように語の途中で切れることも、逆に頻出語がまるごと1トークンになることもあります。覚えるべきは境界そのものではなく、「文字数ではなくトークン数で数えられている」ことです。

窓は「広ければ安心」ではない

たとえるなら

作業机の広さです。机に置ける紙の量は決まっていて、そこに全部を並べないと仕事ができません。はみ出したら、古い紙を捨てるか、要約した1枚に置き換えるしかありません。

現実に起きること ログ検索ツールが5万行を返す → その5万行が会話履歴に残り続ける → 数回のやり取りで机が満杯 → 最初に置いた指示を捨てるしかなくなる。
対策は「ツール側で必要な行だけ返す」。机に載せる前に減らすのが一番効きます。

「窓が大きい＝安心」ではない

誤解「窓が広いモデルを使えば、何でも詰め込んでよい」 実際は詰め込むほど遅く・高くなり、大事な指示が埋もれて効きにくくなる。広く使うより、何を入れるか選ぶほうが結果が良くなる（Domain 5）。

ポイントウィンドウは共有資源。ツールの定義文も、ツールが返した長大なログも、同じ窓を食う。

プロンプトキャッシュ

同じ前半は、使い回せる

毎回まるごと送り直しますが、前半が前回と同じなら計算をやり直す必要はありません。これがプロンプトキャッシュです。

▶ 並べ方を切り替えて、2回目の負担を比べる
1回目のリクエスト
2回目のリクエスト（1文だけ足した）

画面の読み方

  1. 1上の帯が1回目、下の帯が2回目（1文だけ足した状態）。
  2. 2緑が前回と先頭から一致している範囲。ここは計算をやり直しません。
  3. 3橙が今回足された分。計算するのはここだけです。
  4. 4「冒頭に日付を入れる」に切り替えると緑が消えます。先頭が変わると、後ろ全部が作り直しになるからです。

ポイントキャッシュは「先頭から一致している範囲」だけ効く。1文字でも前を書き換えると、そこから後ろは全部作り直しになる。だからDomain 4の「長い資料は先、指示は後」は、精度だけでなくコストの話でもある。

キャッシュが崩れる3つの場合

よくある失敗 プロンプトの冒頭に 今日は2026年8月6日です と入れている。
→ 日付は毎日変わる。つまり毎日、先頭から不一致になり、後ろにどんなに長い資料があってもキャッシュが1度も効かない。

「会話を続けているだけなら、勝手に効くのでは？」

そのとおりです。会話履歴は追記しかされないので、前回送った内容がそのまま今回の前半になります。ふつうに会話を続けている限り、何も意識しなくてもキャッシュは効きます。順番を自分で設計する必要があるのは、会話ではなく「1回きりのリクエストを何本も投げる」ときです（同じ長い資料に対して、質問だけ変えて何十本も投げるような場合）。

ただし「不変だから常に効く」とまでは言えません。崩れるのは次の3つです。

・履歴を書き換えたとき　要約して圧縮する、古い発言を削る、途中のツール結果を差し替える。どれもその地点から後ろが作り直しになります。Domain 5の「溢れそうなら圧縮する」は、同時にキャッシュを捨てる行為でもあるということです。
・前段を変えたとき　キャッシュは「ツール定義 → システム指示 → 会話」の順に積まれていて、上を変えると下が全部無効になります。会話履歴が同じでも、ツールを1つ足しただけで全滅します。
・時間が空いたとき　キャッシュには有効期限があり、既定では数分程度です（より長く保つ設定もありますが、そのぶん割高になります）。翌日また続きから、では効きません。

だから並び順が効く

変わらないもの（役割の説明、道具の定義、参照する資料）を前に、変わるもの（今回の質問、今日の日付）を後ろに置く。これだけで、読ませる資料が長い用途ほど効果が大きくなります。Domain 4で「長い資料は先、指示は後」と出てきますが、あれは精度の話であると同時に、ここでのコストの話でもあります。

ポイントキャッシュは「先頭から一致している範囲」だけ効く。1文字でも前を書き換えると、そこから後ろは全部作り直しになる。だからDomain 4の「長い資料は先、指示は後」は、精度だけでなくコストの話でもある。

実物を見る ─ cache_control で区切りを打つ

「ここまでを使い回す」と明示するためのフィールドです。効いたかどうかは usage を見て判断します。

リクエスト ─ 長い資料の末尾に区切りを打つ

{
  "system": [
    { "type": "text",
      "text": "…長い社内マニュアル…",
      "cache_control": { "type": "ephemeral" } }1
  ],
  "messages": [ { "role": "user", "content": "返品の期限は？" } ]
}

応答の usage ─ ここで効き目を確かめる

"usage": {
  "cache_creation_input_tokens": 5120,2
  "cache_read_input_tokens": 0,3
  "input_tokens": 50 }
  1. 1このブロックまでがまとめてキャッシュ対象になります。区切りは1リクエストにつき最大4つまで。
  2. 2作ったトークン数。1回目はここに数字が出ます。書き込みは通常の入力より割高です。
  3. 3読めたトークン数。2回目以降ここに数字が入り、input_tokens が小さくなります。効いたかどうかはこの値で判断します。
  4. 4有効期限は既定で5分。"ttl": "1h" を足せば1時間保ちますが、そのぶん単価が上がります。

ポイント効いたかどうかは usage.cache_read_input_tokens で確かめる。区切りは最大4つ、既定の有効期限は5分。

※ 短いプロンプトはそもそもキャッシュされません（モデルごとに最小トークン数が決まっています）。また、会話をふつうに続けている場合は明示しなくても自動で効きます。cache_control を自分で打つのは、同じ長い前半に対して1回きりのリクエストを何本も投げるときです。

セクション

確率で次の1トークンを選ぶ

Claudeは「次の1トークン」を確率で選び続けている

文全体を先に決めているのではなく、1トークンずつ「次に来そうなもの」を選んでは繋げています。実際に選んでみてください。

▶ 候補をひとつ選ぶと、末尾に足されて次の候補が出ます（数値は説明用の例です）

画面の読み方

  1. 1上の枠がここまでの文章。最初は「今日の天気は」だけです。
  2. 2下の4行が次に来る候補と、その「らしさ」の数値。棒の長さがそのまま確率です。
  3. 3どれかを押すと、それが末尾に足され、その新しい文章をもとに次の候補が計算し直されます。候補は毎回変わります。
  4. 43回選ぶと文が終わります。文全体を先に決めたのではなく、3回の選択の結果としてその文になった ─ これが生成の実体です。

大事なのは、Claude は「正しさ」ではなく「もっともらしさ」を最大化しているということです。事実を照合してから答えているわけではありません。

ポイントこの選択の繰り返しが生成の実体。だから同じ質問でも答えは毎回わずかに揺れるし、もっともらしい嘘も起こりうる。確実性が要るところは、モデルの外側（コードによる検証など）で担保する。

では、どう付き合うか

これで説明がつくこと ・同じ質問でも答えが毎回少し違う → 選択が確率的だから
・存在しない関数名を、いかにも本物らしく作ってしまう → 「それらしい並び」を選んだ結果であって、嘘をつく意図があるわけではない
・自信ありげな口調と正しさは無関係 → 口調もまた「もっともらしい」から選ばれている

では、どう付き合うか

この性質は消せません。消せない前提で、外側を設計します。事実が要るなら道具で取りに行かせる（Domain 1）、形が要るならスキーマで受け取る（Domain 4）、絶対に守らせたいならコードで塞ぐ（Domain 2・Domain 5）。この教材の残りは、ほぼこの1点への対処と言ってもかまいません。

ポイントこの選択の繰り返しが生成の実体。だから同じ質問でも答えは毎回わずかに揺れるし、もっともらしい嘘も起こりうる。確実性が要るところは、モデルの外側（コードによる検証など）で担保する。
