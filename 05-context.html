コンテキスト管理と信頼性

出題比率 15%

セクション

窓が埋まったら

窓が埋まってきたら、削るか要約する

長い作業では履歴が必ず膨らみます。何を残すかを決めるのが「コンテキスト管理」です。

図の読み方

  1. 1上の3本の帯が、作業が進むにつれて窓が埋まっていく様子です。1本目は余裕がありますが、3本目でほぼ満杯になっています。
  2. 2そこから下に2つの道があります。左が要約して圧縮する。決定事項・未解決点・次の手順だけを残します。
  3. 3右がそもそも入れない。巨大なログは必要な行だけ返す、あるいは別に逃がす（後述のサブエージェント）。
  4. 4効くのは右のほうです。載せてから減らすより、載せる前に減らすほうが確実だからです。

ポイント要約は「短くする」ことではなく「次の判断に必要なものを選ぶ」こと。決定・制約・残タスクが残っていればよい。

机の片付けにたとえると

たとえるなら

机が一杯になったときの片付けです。全部捨てるのでも全部取っておくのでもなく、この先の作業に必要な紙だけ残す。要約とは短くすることではなく、選ぶことです。

残すもの／捨ててよいもの 残す：決まったこと（採用した方針）、制約（やってはいけないこと）、未解決の点、次の手順
捨ててよい：試行錯誤の途中経過、読み終わったログの本文、失敗して破棄した案の詳細

もうひとつ、そもそも机に載せないという手があります。ツールが返す量を絞る、調べ物は子に任せて要約だけ受け取る（後述のサブエージェント）。載せてから減らすより、載せる前に減らすほうが確実です。

誤解「圧縮すればいいのだから、履歴は膨らんでも問題ない」 実際は圧縮は履歴を書き換えるので、その地点から先のプロンプトキャッシュが無効になります（前提編）。ただではありません。

ポイント要約は「短くする」ことではなく「次の判断に必要なものを選ぶ」こと。決定・制約・残タスクが残っていればよい。

セクション

サブエージェント

別のコンテキストで作業させ、結果の要約だけを持ち帰る。本体の窓を汚さずに済みます。

図の読み方

  1. 1左が親。中の行が2本しかないのは、窓がきれいなままだという意味です。
  2. 2中央が子。行がびっしり詰まっています。大量の検索・読み込みで自分の窓を使い切っていますが、これは子の窓です。
  3. 3親から子への矢印が指示。ここで必要な前提を渡します。
  4. 4子から右への矢印が要約だけを返すところ。5万行を読んでも、返るのは数行です。
  5. 5上の点線が、その要約が親に戻る経路。親の履歴に入るのはこれだけです。

たとえるなら

部下に調べさせて、要点だけ報告してもらうのと同じです。部下の机がどれだけ埋まろうと、こちらの机には報告書1枚しか残りません。

親の指示に必ず含めるもの ・何を調べてほしいのか（目的）
・すでに分かっていること・決まっていること（親だけが知っている前提）
・どんな形で返してほしいのか（成果物の形式）
3つ目を書かないと、長文の報告が返ってきて結局こちらの机が埋まります。
誤解「子は親のやり取りを見ているので、説明は省ける」 実際は見ていません。渡し忘れた前提は、そのまま誤った成果物として返ってきます。

ポイント子は親の履歴を自動では引き継がない。必要な前提は、指示の中に明示して渡す必要がある。

セクション

確実にしたいことは仕組み側へ

「必ず起きてほしいこと」はモデルに頼まない

お願いは守られないことがあります。必ず実行したい処理は、仕組み側（フック等）で自動的に走らせます。

図の読み方

  1. 1左（赤）がお願いするやり方。「編集したら必ず整形して」とプロンプトに書きます。
  2. 2結果は下の3行のとおり。だいたい守るが、忘れることがあり、回数が増えるほど取りこぼす。100回編集すれば数回は抜けます。
  3. 3右（緑）が仕組みで走らせるやり方。「編集ツールの実行後に整形を起動」という形で、モデルの判断を通しません。Claude Code ではこれを hooks（フック） と呼びます（Domain 3）。
  4. 4結果は100%走る・気分に左右されない・ログにも残る。判断が要らない処理を、判断できる相手に頼む必要はありません。

ポイント判断が要ることはモデルに、要らないことはコードに。この線引きが、そのまま信頼性の設計になる。

仕組み側に移すもの

たとえるなら

「退室時は施錠してください」の貼り紙とオートロックの違いです。貼り紙はほとんどの人が守りますが、急いでいる日に忘れる人が出ます。オートロックは忘れることができません。

仕組み側に移すもの ・編集したら整形する／リンタをかける
・コミット前にテストを走らせる
・危険なコマンドの実行を止める
・実行内容をログに残す
どれも判断が要りません。判断が要らないものを、判断できる相手に頼む必要はありません。

この線引きは、そのままこの教材全体の背骨です。判断が要ることはモデルへ、要らないことはコードへ。

ポイント判断が要ることはモデルに、要らないことはコードに。この線引きが、そのまま信頼性の設計になる。
