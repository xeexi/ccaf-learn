ツールを渡すとは、説明書を渡すこと

ツールを使えるようにする＝関数を渡すのではなく、「こういう道具があります」という説明をプロンプトに同梱することです。

図の読み方

  1. 1左の箱がアプリが用意するもの。3行で1つの道具ぶんです。名前・どんなときに使うか・引数の形。
  2. 2矢印の「同梱」は、質問と一緒に毎回送られるという意味です。1回登録して終わりではありません。会話のたびに、道具の数だけそのまま送り直されます。
  3. 3中央の Claude は、それを読んで今回使うかどうかを決めます。判断に使えるのは description の文章だけで、道具の中身も実際の挙動も見ていません。
  4. 4右の「これを使いたい」が tool_use。ここで応答は終わり、こちらに返ってきます。この時点で検索は1件も走っていません。

つまりこの図の中で、実際に何かが起きている箇所はひとつもありません。起きるのは、返ってきた要求をアプリが実行する次のページからです。

ポイントdescription は「人間向けのメモ」ではなく、Claudeが使う／使わないを判断する唯一の材料。ここが曖昧だと道具は正しく選ばれない。

→ 何をするかは分かるが、いま呼ぶべきかが分からない。返金の相談中に呼んでよいのか判断できない。

○ description: "注文の配送状況を検索する。配送状況・到着予定を答える前に必ず呼ぶこと"
→ 呼ぶ条件が書いてあるので、迷わない。

エージェントループの1周

「モデルが要求 → アプリが実行 → 結果を返して再びモデルへ」。この4手が1周です。1手ずつ進めて、会話がどう伸びるかを見てください。

▶ ボタンを押すと1手進み、下に会話が積み上がります

図の読み方

  1. 1モデルが考える。まだ外には何も起きていません。
  2. 2tool_use を返す。要求が応答として返り、ここでモデルの処理はいったん終わります。（下のログに出てくる stop_reason は、このすぐあとで扱います）
  3. 3アプリが実行する。この間モデルは動いていません。待っているのではなく、呼ばれていないだけです。
  4. 4tool_result を返す。結果を末尾に足して、もう一度送ります。
  5. 5①に戻る。ただし「続きから再開」ではなく、伸びた履歴をまた最初から読み直しています。

矢印は「処理の担当が移る向き」であって、データが自動で流れているのではありません。動かしているのは常にアプリ側です。Claude が書いたのは②と⑤だけで、③④はすべてコードの中の出来事です。

ポイントtool_use を受け取ったら、必ず対応する tool_result を返して会話を続ける。返さずに次の質問を足すと、会話は壊れる。

「依頼する側」がねじれて見える

「依頼する側」がねじれて見える

通信の形でいえば、アプリがクライアント、モデル側がサーバです。接続を開いてリクエストを送るのは、いつもアプリのほうです。

ところが②では、モデルが「これを実行してほしい」と依頼し、アプリが実行して報告しています。通信では問い合わせる側だったアプリが、仕事の中身では受ける側になっている ─ ここがねじれて見える理由です。

帰結モデルは自分から接続を開けないので、聞かれたときにしか要求を出せません。アプリが次のリクエストを送らなければ、モデルは何もしません。待っているのですらなく、処理そのものが終わっています。「エージェントが勝手に動き続ける」ことが構造上ありえないのは、これが理由です。
④を返し忘れるとどうなるか 「A-12を調べて」と頼んだのに、返事が来ないまま次の話をされる状態です。
Claude 側から見ると頼んだ仕事の結果が永久に来ないので、会話の筋が通らなくなります。API が形式エラーを返すこともあります。
誤解「ループを回す＝Claude が自律的に動き続けている」 実際は回しているのはアプリ側の while 文。だから「5周までで打ち切る」も自由に書けます。

stop_reason で分岐する

ループを回すか止めるかは stop_reason が決める

応答には「なぜ止まったか」が必ず付いてきます。値を選んで、アプリが次に何をすべきかを確かめてください。

▶ 返ってきた値を選ぶ

図の読み方

  1. 1上の箱が1回ぶんの応答。応答には stop_reason が必ず1つ付いてきます。付かないことはありません。
  2. 2下に伸びる4本が取りうる値。アプリは値を見て、対応する枝の処理をするだけです。
  3. 3このうちループに戻るのは tool_use の枝だけ。ほかの3本はループから抜けます。ループの図が繰り返されるかどうかは、ここで決まります。
  4. 4値は応答の決まった場所に入っています（「実物を見る②」で現物を見ます）。本文を読んで判断する必要はありません。

とくに max_tokens は見落とされがちです。これは「答え終わった」ではなく「途中で切れた」を意味します。end_turn と同じ扱いにすると、尻切れの文章をそのままユーザーに見せてしまいます。

ポイント「Claudeの返事を文字列で判定して分岐」はアンチパターン。分岐はこの構造化された値だけで決める ─ ここは確率ではなく、決定的に書ける部分。

値ごとの扱いと、よくある誤解

アプリ側の分岐は、これだけで書ける if stop_reason == "tool_use": ツールを実行して結果を返す
elif stop_reason == "end_turn": 画面に表示して終わり
elif stop_reason == "max_tokens": 途中で切れている。続きを促す
誤解「返事に『検索します』と書いてあったら検索すればいい」 実際は言い回しは毎回揺れます（「調べますね」「確認いたします」「Let me search」…）。揺れない値で分岐するのが鉄則です。

誰が、何を送っているのか

「どちらからどちらへ、何が渡ったか」を時間順に並べた図です。

図の読み方

  1. 1アプリが送る。中身は system・tools・messages だけ。接続を開けるのはこちら側だけです。
  2. 2モデルが返す。tool_use と stop_reason は返ってくる側のもので、こちらから送るものではありません。ただしこの2つは扱いが違います。tool_use は content の中身なので次の往復で履歴として送り返しますが、stop_reason は content の外側にあるメタデータで、履歴には入りません。つまり窓（コンテキストウィンドウ）も食いません。usage や id も同じです。
  3. 3アプリがDBを引く。このやり取りはモデルからは見えません。
  4. 4アプリがまた送る。中身は1回目の全部＋前回の応答＋ tool_result。増えているだけで、形は①と同じ。
  5. 5モデルが最終的な答えを返す。stop_reason は end_turn。

ポイント送るのは messages、返るのは content と stop_reason。この向きさえ固定して覚えれば、あとの章はすべてこの上に乗る。

向きを取り違えないために

モデルの縦線に付いた灰色の帯（②〜④の間）を見てください。この間、モデルは動いていません。待っているのではなく、②で処理が終わっているだけです。次に動くのは、アプリが④を送った瞬間です。

誤解「アプリが tool_use を送り、以降は stop_reason を送り続ける」 実際は向きが逆です。アプリが送るのは常に messages（その中に tool_result を入れる）。tool_use と stop_reason は、毎回モデルから返ってくる側です。stop_reason は「以降ずっと」ではなく、1回目の応答にも付いています。

カードゲームにたとえると

札に触れない助言者に相談していると考えてください。①〜⑤がそのまま次の3つに対応します。

・手札を読み上げる＝ツール定義。相手は前のターンの手札を覚えていないので、毎ターン読み上げ直します（前提編の「毎回まるごと送り直す」）。
・「この札を切って」という指示＝tool_use。言うだけで、相手は札に触れません。切るのはいつもあなたです。
・切った結果を伝える＝tool_result。

つまずきやすいtool_result を「切ったあとの盤面」と考えると、少しずれます。盤面が自動で見えるわけではありません。あなたが言葉にして渡した分だけが、相手の知る情報になります。だからDomain 5で「ツールが返す量を絞る」という設計の話になります。 この比喩の外実際の tool_result にはどの指示に対する結果かを示す id を付けます（「実物を見る③」）。指示が同時に複数出ることがあるためで、1手ずつ進むカードゲームでは表せない部分です。
3往復すると、どうなるか ①④のような青い矢印が3本になり、そのたびに messages が長くなります。
橙の矢印も3本で、最後の1本だけが end_turn、それまでは tool_use です。
ループが回るとは、この青と橙の往復が増えることにほかなりません。

ポイント送るのは messages、返るのは content と stop_reason。この向きさえ固定して覚えれば、あとの章はすべてこの上に乗る。

ループが壊れるとき

実装ミスの多くは、この3つのどれかです。

図の読み方

3つとも、「ループの1周」で見た①〜④のどこかが崩れた形です。どの手が壊れているかで見てください。

  1. 1終わらない（②が繰り返される）　同じ検索語のまま何度も tool_use が返り続ける状態。原因の究明は後回しでよく、まず反復回数に上限を置いて止めます。一番単純で確実な対処です。
  2. 2結果を返し忘れる（④が抜けている）　図の点線の枠がそれです。実装漏れとしては地味ですが、症状は「会話が突然おかしくなる」なので、原因にたどり着きにくい種類の不具合です。
  3. 3窓が溢れる（④が大きすぎる）　ツールが返した巨大なログをそのまま積むと、数往復で窓が埋まります。返す前に必要な行だけに絞るのが正解で、Claude に「要約して」と頼むのではありません。頼んだ時点で、もう全文が窓に載っているからです。
試験でのねらわれ方 「エージェントが暴走している。最初に取るべき対処は？」という設問で、「より大きなモデルに変える」「アーキテクチャを作り直す」は誤答になりやすい選択肢です。反復上限のような、小さくて確実な手が正解になります。

ポイント試験では「一番単純で効く対処」が正解になりやすい。まずは反復上限・結果の整合・返す情報量の3点を疑う。

セクション

1体か、分けるか

複数に分けると強くなるとは限りません。分けるほど、渡し忘れと統合の失敗が増えます。

図の読み方

  1. 1「この3つに当てはまるか」（左）── 判断の条件です。3つとも「分ける理由があるか」を問うています。「分けたほうが速そう」は理由に入りません。
  2. 2「1つでも当てはまる」（右上・緑）── 分けて子に任せます。3つ全部そろう必要はありません。
  3. 3「どれも当てはまらない」（右下）── 1体のまま。分けません。
  4. 4下の赤い帯が分けた瞬間に生まれる新しい失敗。前提の渡し忘れと、結果の統合ミスです。分ける前には存在しなかった不具合が増えます。

とくに条件①は重要です。別々に大量の資料を読む作業は、分けないと窓が共倒れになります（Domain 5）。

分けない例／分ける例 ✗ 3つのファイルに、決まった順で同じ修正を入れる → 1体でよい。順番も内容も決まっていて、読む量も少ない
○ 10個のリポジトリを、それぞれ独立に調査する → 分ける。互いに待つ必要がなく、それぞれ大量に読む
誤解「複数エージェント構成＝高度で優れた設計」 実際は分ける理由がないのに分ければ、ただの劣化です。渡し忘れと統合ミスだけが増えます。

ポイント「複数エージェントにすべきか」を問う設問では、単純な1体で足りる選択肢が正解のことが多い。分けるのは理由があるときだけ。

セクション

親子の形

子どうしは直接やり取りしません。全体を知っているのは親ひとりだけ、という形にします。

図の読み方

  1. 1中央が親。自分では調べず、段取りと統合だけを担当します。
  2. 2周囲の3つが子。それぞれ別の窓・別の履歴を持っています。子がどれだけ大量に読んでも、親の窓は汚れません。
  3. 3親と子を結ぶ線が指示と報告。情報はすべてここを通ります。
  4. 4子どうしを結ぶ点線に✕。直接のやり取りはありません。
  5. 5これが並列と統合の形です。ただし速くなるのは待ち時間だけで、トークンの総量は減りません。子が読んだ分は、子の窓で消費されています。

この形の利点は、全体像を持っている場所が親1点に決まることです。子を増やしても、親の段取りだけ見れば全体を追えます。

子Aの発見を子Bに伝えたいときは？ 直接渡せません。親が受け取り、要約して、あらためて子Bへの指示に含めるという形になります。
遠回りに見えますが、これがあるから「なぜその結論になったか」を親の段取りだけで追えます。
誤解「子は親の会話を引き継いでいる」 実際は子はまっさらな状態で始まります。渡し忘れた前提は、そのまま誤った成果物になって返ってきます。ここが実務で最も多い失敗です。

ポイントこの形の利点は「誰が全体を知っているか」が1点に決まること。子を増やしても、親の段取りだけ見れば全体が追える。

固定チェーンか、動的分解か

毎回同じ順番でよい仕事は、モデルに考えさせずコードで並べます。対象が毎回変わる仕事だけ、その場で分けさせます。

図の読み方

  1. 1左（緑）が固定チェーン。抽出 → 検証 → 出力が、毎回この順で流れます。枝分かれがありません。
  2. 2順番が決まっているので、どこで詰まったか分かり、テストもできます。結果もぶれません。
  3. 3右が動的分解。親がその場で仕事を割るので、枝の数も中身も毎回変わります。
  4. 4下の一文が、それぞれ向く仕事です。判断の基準はひとつ ─ 「毎回やることが決まっているか」。
どちらを選ぶか 毎月の請求書処理（項目は毎回同じ）→ 固定チェーン。抽出 → 検証 → 出力をコードで並べる
未知のバグの原因調査（どこを見るか毎回違う）→ 動的分解。親がその場で調べる先を割り振る
誤解「動的に分解できるほうが賢いから、そちらが良い」 実際は柔軟さの代償は結果のばらつきです。決まった手順を動的にするのは、まさに試験で誤答になる過剰設計です。

ポイント柔軟さには「結果がばらつく」という代償がある。決まった手順を動的分解にするのは、まさに過剰設計。
